gRPC #38002: reporter CPU profile review

Reporter CPU profiles analyzed; a cause and repair remain unverified.

The original 60-second C++ and Java recordings were analyzed offline. No local server workload was run.

Upstream issue · Case record

Observed problem and existing evidence

The reporter observes higher C++ server CPU use at a stated 60 TPS. The attachment contains binary perf data, text stacks and flame graphs for both implementations.

Reporter profile analysis

The text event headers match the binary perf records by thread ID, timestamp and period. Values below count recorded samples, not requests.

C++ inclusive path counts: request handler 1,165; subscriber handler 388; response Finish 612; CompletionQueue 212. These groups overlap. This does not isolate one dominant cause.

The C++ libraries occur under debug paths, which motivates checking build flags; the paths do not prove an unoptimized build. Java records substantial compilation activity and lacks many JIT symbols. Sample totals are not a validated per-RPC CPU ratio.

The CoroPerf perf-script reader was corrected to retain thread names containing spaces. Its regression passes; the resulting 3,515/801 event totals match an independent binary read. No creation edges were fabricated.

Competing explanations

HypothesisDiscriminating evidence
H1 · Build configuration contributes to the difference.Obtain compiler flags and matched shared libraries; compare optimized and original C++ builds with the same application workload. A debug directory name alone is insufficient.
H2 · Application work and warmup differ.Match payloads, completed RPC counts and handler behavior; collect both profiles after a documented warmup.
H3 · Runtime or completion-queue overhead remains after matching the controls.Measure per-request CPU with queue/tag identities and isolate processing, completion and waiting without adding overlapping inclusive groups.

  • The shown C++ code uses thread-driven CompletionQueue callbacks; coroutine use is not established.
  • A future attribution needs call/tag lifetime, queue, executing thread and callback generation, not just matching addresses.

No coroutine or request ancestry is claimed for this offline profile review.

Reproduction and controls

  1. Recover exact build flags, ELFs, Java JIT maps, server sources and the submitted load configuration.
  2. Compare the same implementation with a cause-specific change under matched warmup and observed completed RPC counts.

Next action and limits

Verify the actual C++ optimization flags and reproduce the original application comparison before choosing a repair.

No local incident run or validated repair. Missing ELFs, JIT maps, completed RPC counts and callback identities prevent a root-cause conclusion or a coroutine-debugging success claim.
