Issue findings

Local observation
Both requests schedule three prefill tokens and finish with the same output token. With supplied clocks, the legacy EngineCore result-wait timing reports 2 and 0 ms. The worker timer introduced by PR #61690 reports 28 and 12 ms from paired stream events. Both records arrive after the two replies, in one later stats-only packet. A subsequent packet contains only the dummy record.
What CoroPerf showed
The two timer-read samples have identical physical frames. Matching the exact scheduling snapshot in each pending timing restores the schedule stack. Matching the real Request object at scheduling back to the Task that submitted it restores the caller. The interactive path is 4 → 2 → 0 and the batch path is 5 → 3 → 1. Reversing submissions swaps the attribution even though the counts and timing slots are the same.
Scope and limits
This CPU replay uses the pinned scheduler, timing decorators, dummy-batch stats publication and asynchronous frontend queue read. The model outputs and event timestamps are controlled inputs. The displayed times describe the boundary comparison with those inputs. CUDA timing requires supported iteration logging. The timing PR merged and the broader RFC remains open.
