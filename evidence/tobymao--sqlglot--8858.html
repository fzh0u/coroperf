Issue findings

Local observation
On the reporter’s DuckDB example, two distinct timestamps fell on October 30. The original query returned October 30 twice and October 31 once. The reported commit and the parent of the fix returned October 30 only once after optimization. The fix and release v30.28.0 preserved all three rows.
What CoroPerf showed
The recorded stack leads from eliminate_joins through _should_eliminate_join to _is_joined_on_all_unique_outputs. A Cast node reported the name of the timestamp column. The affected check accepted that name as proof of uniqueness and authorized removing the join. The fixed check requires a Column node. With the same flight data, the fixed query preserved all 39 matches on February 28. Joining directly on an already unique date remained safe in every build.
Scope and limits
The additional calendar workload uses 2,000 public flight records, 1,920 distinct minute-level timestamps and one added day with no flights. Each result was checked against an independent per-day timestamp count. All four builds ran on CPython 3.12.4 and DuckDB 2.0.0. The optimizer runs synchronously. The function stacks were imported from CPython return events, with local values and SQL results recorded separately.
