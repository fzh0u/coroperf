Issue findings

Local observation
The reporter inserted two names in SQLite, 'a' and NULL. On the reported revision, the 1.1.9 wheel and the immediate fix parent, awaiting name__not=None printed [None]. Both the SQL reference and a Python check on the two stored values selected ['a']. The landed source returned ['a']. A separate check on the same connection added an empty string, a second 'a', 'b' and another NULL. Four rows had non-null names. The affected builds selected the two NULL rows, IDs 2 and 6. The fix selected IDs 1, 3, 4 and 5, including the empty string. Explicit null checks and comparisons with 'a' agreed across all four builds.
What CoroPerf showed
The affected filter function received None and returned an inequality with NULL joined by OR to IS NULL. The resolver received the same criterion object. SQLite evaluated the resulting expression as unknown on 'a' and true on NULL, so only the NULL row survived. The landed source returned field.notnull() for the same argument. The emitted SQL spelled this as NOT "name" IS NULL. On the reported revision, segments 1 and 2 record synchronous predicate construction. Segment 3 records ValuesListQuery.__await__ creating the unstarted _execute coroutine at queryset.py line 1859. Segment 5 samples the live instance while the SQLite client returns the projected row. At segment 6 the same coroutine object and frame return [None], which the original application prints. The corresponding fixed trace returns ['a'].
Scope and limits
The original program uses an in-memory SQLite database and a nullable character column. The four additional inserts and control queries follow the original print calls. The fixed comparison ran the merged source commit. Coroutine identity was measured in the query on the event-loop thread. SQLite’s truth values were checked by running SQL on backups of the original connection.
