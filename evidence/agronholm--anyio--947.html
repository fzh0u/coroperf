Issue findings

Local observation
One bounded cached AnyIO4.8.0/CPython3.11.11 component retains the maintainer test ordering: the controller holds CapacityLimiter(1), starts two borrowers, cancels the first scope before releasing, then waits100ms for the second signal. The second borrower remains queued with borrowed_tokens=0 and tasks_waiting=1. TaskGroup cleanup returns and the process exits0. The target ran once; no fixed-version or repeated workload ran.
What CoroPerf showed
Actual Event arguments and current Task IDs distinguish the two borrower submissions. Read-only limiter statistics and queue snapshots identify the second Task as the remaining waiter. Its unique runtime generation joins creation2 to wait4 through an explicit base_to_sample edge. CoroPerf recovers the real second tg.start site test_acquire_cancelled:47, absent from both native get_stack and the current await-chain samples. Native state already establishes idle capacity with a waiter; the added diagnostic value is historical submission attribution.
Scope and limits
The report names4.9.0; this is a historical4.8.0 component, not exact-version or production confirmation. Primitive Task/Event/queue observations add timing work but no await. The public completion Event is distinct from the internal queue Event, whose identity was not captured. Only the100ms window is established. Task snapshots are not CPU samples; generic creation does not prove resource ownership. The original failure is exported as data with cleanup; process exit0 is not an upstream passing test. No natural-race frequency, instrumentation baseline, root-cause discovery, repair experiment or optimization result is claimed.
