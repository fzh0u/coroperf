Issue findings

Local observation
A Celery 5.3.1 producer submitted ten tasks numbered 0 through 9. All ten completed successfully. We released them in a known, nonsequential order. With descending task IDs the callback received 9 through 0. Independently reading the Redis sorted set after each of the first nine writes showed that every stored result had the same score.
What CoroPerf showed
The producer stack shows group._prepared calling Signature.freeze without a group index for generator tasks. All ten broker messages carried a null index. On the worker, RedisBackend.on_chord_part_return converted each missing index to positive infinity. Redis then sorted equal-scored members by their encoded bytes, which include the task ID. The gevent creation stack and the result-write stack identify the same worker greenlet. Changing just the producer to 5.3.4 restored input order with the 5.3.1 worker.
Scope and limits
The experiment used Redis for message transport and results. The reporter used RabbitMQ for transport. The generated-ID case ran freely. Controlled IDs and completion gates distinguish submission order, completion order and Redis ordering. Function stacks were captured in separate runs of the released Python packages using observer callbacks.
