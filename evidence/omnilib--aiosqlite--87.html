Issue findings

Local observation
Each run used one SQLite connection for 24 concurrent upserts. Twelve new projects got their own row IDs. Of the twelve updates, one read zero and eleven read a positive ID belonging to another project. Reopening the database confirmed the row actually updated in every case.
What CoroPerf showed
The capture joins each asyncio task created by gather in measure to its lastrowid getter and the value it returned. For example, project 12 returned 0 and committed to row 12. The original database controls explain how that can happen. A conflict update preserves the connection’s last successful insert ID, which CPython copies into the cursor at execution time.
Scope and limits
Task identities come from the local concurrent workload that used the published SQL. The upstream comment used synchronous sqlite3. Two traced runs each matched all 24 tasks. Diagnosing the stale ID also required the insert history and the committed rows.
