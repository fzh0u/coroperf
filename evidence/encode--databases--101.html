Issue findings

Local observation
Using databases 0.2.2 and asyncpg 0.18.3, reading row['id'] returned 101. The same row converted to an empty dictionary and tested false. A SQLAlchemy expression selecting the same four fields returned all four. The error also reproduced on 0.2.4. Version 0.2.5 returned four fields for both queries.
What CoroPerf showed
The same returned row reached Record.__iter__ and Record.__len__. For raw SQL the compiler supplied zero column names, even though the driver held four values. The old methods used the compiler’s column list. The fix reads the underlying asyncpg record. In the two-depot run, each task’s creation in dispatch_snapshot was matched to the iteration of the rows that task actually fetched.
Scope and limits
The original report supplies the API calls and dependency versions. The local run used a PostgreSQL 10.23 server with four inventory rows. The paired task origins come from the concurrent depot reads. Restoring the database dump and changing one quantity from 0 to 9 independently confirmed the driver and fixed mapping returned the new value.
