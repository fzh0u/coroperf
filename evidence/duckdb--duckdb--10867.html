Issue findings

Local observation
The reporter inserted two observations: time 0 with value 0, and time 1 with a NULL value. The right-hand subquery kept only non-NULL values. Each left time should therefore match right time 0. DuckDB 0.10.0 and 0.10.1 returned only the first row. Both returned the second row when the eligible right input was materialized before the join. DuckDB 0.10.2 returned both rows for the original SQL. Independent Python and SQLite computations agree.
What CoroPerf showed
The native optimizer resolved the predicate to the right-hand value column on both versions. On 0.10.1, FilterPushdown::PushdownInnerJoin returned a filter above the ASOF join. PhysicalAsOfJoin::Sink received both right rows. The native join matched left time 1 to right time 1, and PhysicalFilter::ExecuteInternal then discarded its NULL value. On 0.10.2, the filter ran on the right input. Only time 0 reached the sink, so both left times matched it. The regression test failed on the parent commit and passed on the merge.
Scope and limits
The reporter used 0.10.1-dev397 on Linux. We ran the posted SQL on three stock release wheels and the upstream test on the immediate source parent and merge. The debugger sampled the reporter query and controls on 0.10.1 and 0.10.2. The second table uses a separate transaction with tagged quotes to show which lookups lose a valid price as NULL records arrive. The captured native stacks show optimizer and execution functions. This case has no verified coroutine origin.
