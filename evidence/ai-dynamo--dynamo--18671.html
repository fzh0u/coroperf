Issue findings

Local observation
With a two-second idle interval, the median time from registration to Ready is 2,003–2,005 ms on the base and 5.1–5.2 ms with open PR #18672 for a worker that succeeds on its first check. For the worker that fails once, the medians are 4,007 ms and 1,006–1,008 ms. In one separate comparison at the default ten-second setting, the successful worker reaches Ready in 10.004 s and 4.8 ms. The retrying worker reaches Ready in 20.005 s and 1.004 s. It stays NotReady after its first failure in every run.
What CoroPerf showed
The two native timer-expiry stacks and their spawn stacks are identical on the Tokio thread. Each live Task ID matches the ID returned by its JoinHandle, linking execution records 4 and 5 to creation records 2 and 3. The same registered Arc<Notify> joins the shared spawn site back to records 0 and 1, where the interactive and batch endpoints register. Reversing registration order swaps the launchers attached to those paths on both revisions. The join attributes the identical timer samples to a worker that passes immediately and a worker that must retry.
Scope and limits
The comparison runs the original Rust DistributedRuntime and health-check manager with local fixture engines and in-memory discovery. Timings are registration to the first observed Ready state on one Tokio thread. The two-second measurements use three runs per arm and order and exclude stack collection. The default interval has one comparison. The local experiment has no Kubernetes probe or model-startup time. All 13 baseline and 16 proposal health-check tests pass using their loopback QUIC fixture. The issue and PR are open.
