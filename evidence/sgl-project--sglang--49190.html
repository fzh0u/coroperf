Issue findings

Local observation
Each burst sends eight ordinary text requests of 8,070 tokens through the Rust HTTP frontend. With one tokenizer thread on the base, the median of the longest queue wait per burst is 102.7–103.1 ms across two launch orders. The proposal chooses four workers on the eight-core frontend set, reducing that wait to 12.5–12.7 ms. Manually selecting four workers on the base gives 12.5–12.7 ms as well. The full tokenizer window falls from 125.5–125.7 ms to 34.7–35.3 ms with the proposal. Each encode still takes about 16 ms, and the scheduler receives identical token IDs for every request in all arms.
What CoroPerf showed
On the single-worker base the two native tokenizer execution stacks are identical. The full internal request ID matches each worker dequeue with the same request's enqueue, its Tokio HTTP Task, and the scheduler-ring input. Execution records 3 and 5 join to request creation records 2 and 4. The public ID sent in the local HTTP request and echoed in its response joins each HTTP Task to launcher record 0 or 1. Reversing the launch order preserves both matches. The manual four-worker control attributes the improvement to overlapping tokenization and shorter queue waits.
Scope and limits
The loopback replay runs pinned SGLang Rust HTTP, TokenizerManager, the native tokenizer pool, and the scheduler ring. It uses Google's Gemma 4 31B instruction tokenizer, plain-text /generate, and a local scheduler fixture that returns one real token ID per request. Each arm runs five timed bursts per order after one warm-up. The separate two-request stack capture does not enter those timings. The server, processor, and encoding crate use optimization level 2 with debug information. The measured interval starts at the tokenizer enqueue and ends at the sample or encode completion. The upstream report measures client latency on a GPU deployment. The proposal's upstream pool-size unit test passed locally. The issue and PR are open.
