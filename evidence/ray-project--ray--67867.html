Issue findings

Local observation
For 32 block and metadata pairs, each actor receives 64 backpressure updates with the scalar Ray Data reader and 32 when the known-ready pairs are consumed through the existing native bulk call. Actor event counters confirm the same result in both execution orders. Both arms emit the same ordered rows and check byte accounting against metadata. Median driver CPU times range from 3.60 to 4.63 ms by object and 2.84 to 4.39 ms by pair across runs and requests.
What CoroPerf showed
Both DataOpTask.on_data_ready observations have identical execution frames on the same driver thread. Matching the exact ObjectRefGenerator, executor WorkItem and its returned Future identifies the submitting Task. The catalog observation joins along 4 to 2 to 0, and the research observation along 5 to 3 to 1. Reversing launches swaps ownership of the same driver frames and preserves the per-actor RPC counts.
Scope and limits
The fixture uses Ray 2.58.0, two actual local async actors, one driver worker thread and the real inline DataOpTask path. Its paired reader assumes all declared pairs were produced successfully before the timed drain. The overlapping CPU ranges and actor counts describe this small local experiment. The report's large workload and generic streaming executor integration are outside this comparison. GitHub issue #67867 is open.
