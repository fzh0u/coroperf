Issue findings

Local observation
Completions, Chat Completions and Responses all send a 64-token limit from both the probe and workload on the reported version and the checked main revision. With a per-request override of 17, both send 17. PR #66260, both at its head and applied to the checked main revision, sends probe limit 1 in both controls, keeps the main workload at 64 or 17, and preserves the temperature setting. Across all four revisions, 48 benchmark runs complete successfully.
What CoroPerf showed
The two Chat Completions POST bodies and their socket receive stacks are identical on main. In ClientRequest.send, CoroPerf records the live ResponseHandler and its sending asyncio Task. The callback in record 1 uses that same handler and joins to the probe Task creation in record 0. Record 3 joins to the workload Task creation in record 2 by the same relationship. This identifies a 64-token limit on the one-token probe path even when the wire body supplies no role marker.
Scope and limits
The fixture runs benchmark() with the original scheduling and HTTP clients. A loopback stub sends a fixed one-token stream, so the result establishes requested token limits and request ownership. Generation times on a model and end-to-end serving throughput are unmeasured. The GitHub issue and proposed fix remain open.
