Issue findings

Local observation
The author supplied a two-line file. Running the maintainer’s complete program with the author’s LF endings returned only the header. With CRLF endings the same program also returned the data row, including the quoted JSON field. On an airport CSV, the old dictionary reader returned zero of 3,376 airports. Setting the dialect’s line terminator to LF recovered every field in every record.
What CoroPerf showed
The stack follows the main task into AsyncReader.__anext__ and _read_until. The reader looked for CRLF and passed the entire LF file to a single iteration. The standard CSV reader consumed 71 characters for the header, leaving the 122-character data line unread. The async reader then cleared its buffer. In a separate run, two concurrent imports of identical airport records had distinct creation sites. The LF task lost the records while the CRLF task read all 3,376.
Scope and limits
The issue closed with a documentation change. The later parser change and release 1.2.1 both read LF correctly by default. The author’s initial snippet passed fieldnames to AsyncReader, which raised TypeError. The documented AsyncDictReader variant reproduced the posted dictionary output. The unchanged executable example came from the maintainer. The local run used Linux and CPython 3.9.25. The author used macOS and CPython 3.9.1.
