Issue findings

Local observation
The posted server emits twice to one client. With python-socketio 5.7.2, the client received the message addressed by its session ID. Wrapping that same ID in a list raised TypeError. Release 5.8.0 delivered both messages. In a separate four-client test, the two target rooms had three distinct members. On 5.7.2 none received the joint notification. On 5.8.0 each of the three received it once, including the member in both rooms.
What CoroPerf showed
The Engine.IO task factory trace identifies the coroutine allocated for AsyncServer._handle_event_internal. That same coroutine and frame were executing when AsyncManager.emit tried to look up the list as a room dictionary key. The exception occurred before get_participants yielded any session. The closing commit removed the single room-key check. On the fixed revision, the three distinct session IDs yielded by get_participants match the three receiving clients. The synchronous control already delivered to all three on 5.7.2.
Scope and limits
The original client ran on an ephemeral loopback port with a listener to count receipts and a bounded shutdown. Its original transport negotiation upgraded to WebSocket. The four-client workloads use local room memberships chosen for this experiment. Async clients used WebSocket, and the separate synchronous controls used HTTP polling. The matched origin belongs to the incoming event handler.
