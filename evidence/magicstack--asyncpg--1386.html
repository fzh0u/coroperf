Issue findings

Local observation
One asyncpg0.32.0/CPython3.14.3/private PostgreSQL17.1 run follows the original busy-query example: SELECT pg_sleep(0.5) occupies the Connection, so concurrent BEGIN raises InterfaceError. After the query finishes, the Connection is open and idle but _top_xact still points to that FAILED Transaction. The later transaction sends SAVEPOINT and raises native NoActiveSQLTransactionError, SQLSTATE25P01. Process exit0 and connection/server cleanup succeed. Selection/source/setup/run take115.05s.
What CoroPerf showed
The actual API-returned busy Task object0x73927aac5a90 independently matches the native pending Task snapshot and generic CoroPerf identity. The selected live sample precedes BEGIN failure; the same Task returns before the later SAVEPOINT error. CoroPerf joins creation2 to pending sample40 and recovers launch_busy_query, absent from the native Task stack and both error tracebacks. Additional API observations bind this Task, Connection0x73927aa75150 and failed Transaction0x73927a86e110 across the two failures. The source already describes stale _top_xact; the added diagnostic fact is the exact busy operation and its historical submission context.
Scope and limits
This is the original concurrent-query/pre-send BEGIN component, not Aurora/RDS Proxy, SQLAlchemy, a pool or the cancelled-BEGIN variant. Original Task topology is retained: launch_busy_query only names the existing create_task expression, and the later transaction remains inline in main. Resource identity requires the explicit API observer; generic Task ancestry does not infer shared Connection/Transaction ownership. The native pending stack contains execute, and Python continuation inspection stops at the opaque Cython protocol awaiter. One successful scenario; no reset/fix, pool, proxy, cancellation variant, alternate version or additional batch.
