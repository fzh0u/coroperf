Issue findings

Local observation
With the reporter’s command, the official Linux 3.4.0-rc.2 binary wrote the same 40 JSON records to ./etcd.log and descriptor 2. The two complete streams were byte-identical at 8,732 bytes each. The 3.4.0 binary wrote 39 records to the file and zero bytes to stderr. Both kept stdout empty. Every CLI server successfully stored and returned abc. In two separate embedded-host runs per side with file-only output, the parent copied all 34 etcd records to stderr alongside two host diagnostics. At the fix, stderr contained just the two host diagnostics. The fixed log file had 35 records in the first run and 34 in the repeat.
What CoroPerf showed
The parent received one requested path and combined it with the default stderr sink. Zap opened both for normal log entries. For the first startup warning the same two os.File receivers appeared at syscall.Write, which returned 155 bytes on the file descriptor and 155 on descriptor 2. The fix replaced both destination lists before merging. Only the normal file sink received the warning. The verifier matches the opened objects, live descriptor identities and returned byte buffers to the captured files.
Scope and limits
The reporter used Darwin amd64 and showed an initialized data directory. Our Linux runs used fresh directories and separate output descriptors. The first four startup records give a bounded comparison. Whole-process counts also include normal shutdown and can vary between runs. The source builds identify as 3.5.0-pre on master. The six stock pilot runs, eight new release processes and twelve source-built CLI processes are reported separately. The six native captures establish synchronous CLI startup routing and writes. The reporter also mentioned using the embed package. A separately written host exercised that API and read back stored-value in twelve additional processes.
