Issue findings

Local observation
On Streamz 0.6.1, the reporter's program printed one random number and raised CancelledError. Two stock runs on the parent of PR 399 did the same. The merged fix and release 0.6.2 printed 1,000 distinct values in each run. With 1,000 distinct input strings, the old release also completed. A separate 32-input public-sink control kept only the first scattered Future alive. On 0.6.1 all 32 calls then reached workers despite sharing one scatter key. Releasing that Future after eight results made the ninth emission fail in both runs.
What CoroPerf showed
The random map received a fresh task key on every call. On the old build each repeated 'd' had the same scatter key. The scheduler received a release for that key, forgot it, and found the dependency absent when it processed the new map task. Its cancelled-key message named the same future that raised in Client._gather. The graph links that exception frame to the creation of the same coroutine in Client.sync. The fix disables scatter hashing and gives each emission its own dependency. The lifetime control isolates the effect of retaining a scheduler reference while leaving the non-pure map in place. Worker PIDs, addresses and distinct invocation UUIDs confirm that the 32 delivered replies came from separate calls.
Scope and limits
The report lists Python 3.8.5, Dask 2.30.0 and Streamz 0.6.1. We selected matching Distributed 2.30.0 and ran each local cluster on two CPUs. Trace collection changed the cancellation point: the 0.6.1 traced runs printed four and three values. Random numbers and task IDs vary per process. The 32-emission control uses a worker-identifying function in place of random.random and tests the lifetime of a single strong reference.
