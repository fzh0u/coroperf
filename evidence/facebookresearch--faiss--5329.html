Issue findings

Local observation
In Faiss CPU 1.14.2 and 1.16.0, adding the same two-dimensional offset changed the Panorama result from ID 1 to ID 0. Direct squared Euclidean distance on the translated float32 inputs still selected ID 1. Both candidates received a Panorama score of zero. A radius search also admitted the farther vector.
What CoroPerf showed
The native search stack reaches Panorama::progressive_filter_batch and prune_kernel. For ID 0 the accumulated squared norms were 41522.28515625 and twice the dot product was exactly the same float. Subtraction produced zero. ID 1 also rounded to zero, and the strict comparison against the new zero threshold removed the genuinely nearer candidate. Reversing insertion order changed which physical vector survived. Recentering the already translated inputs restored the correct distances.
Scope and limits
The two-vector release and debugger results agree. The digits table uses the released wheels and the original UCI train/test split. The offsets are controlled perturbations of integer features. All genuine distance ties are accepted. In one of three two-candidate digit reductions, a debug compilation changes the winning ID. Both the standalone and sharded native stacks were captured. The sharded stacks identify OS worker threads. No coroutine origin was verified.
