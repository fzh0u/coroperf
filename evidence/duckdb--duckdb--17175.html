Issue findings

Local observation
The reporter joined two one-row tables and requested a three-column ROLLUP. DuckDB 1.2.2 returned the detail row (1, 1, 1) twice. Both subtotal rows retained 1 in their third column, where SQL requires NULL. DuckDB 1.3.0 and an independent PostgreSQL 14.13 run returned all four expected rows. On 1.2.2, disabling either optimizer pass separately restored both missing subtotals.
What CoroPerf showed
The join made the first and third columns equal in the detail row. ROLLUP still needs to clear the third column while retaining the first at two subtotal levels. On the affected native stack, the unused-column visitor changed the third binding to the first, and the duplicate-group visitor then reduced three grouping expressions to two. EXPLAIN showed two physical group keys. On 1.3.0, both visitors preserved three distinct bindings and EXPLAIN showed three keys. CLI builds of the immediate parent and merged fix isolated the change. On the parent, two of four ordered ROLLUP rows differed from the oracle. Changing only ROLLUP to CUBE gave six differences in eight ordered rows. The merged build matched both oracles.
Scope and limits
GDB sampled synchronous C++ optimizer calls on the posted synthetic input. Function names establish the call path. Entry and return memory reads establish the binding changes. SQL responses and an independent prefix calculation establish which rows were wrong. A separate Palmer penguin workload used 344 observations. On 1.2.2, eight of fourteen rows had incorrect island labels, including the 168-observation Biscoe subtotal. The counts were correct. The published-data reference and its six result sets are documented in upstream/penguins/verification.json.
