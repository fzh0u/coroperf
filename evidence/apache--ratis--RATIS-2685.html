Issue findings

Local observation
The Apache Ozone reporter saw the gap between the applied index and a follower’s reported next index grow. In the local Ratis cluster the client wrote initial, then the leader restarted one follower’s log appender. The client wrote apricot, pear and plum. All three peers held identical copies of each client log entry and had committed and applied through its index. On stock 3.3.1 and on the PR parent overlay, the restarted follower’s next and match gauges stayed at 3 and 2 across the three writes. Its live indices reached 9 and 8 after plum. The landed overlay reported 9 and 8. The other follower on the same leader and the trials that kept both appenders running reported current indices on all three builds. In the separate registry experiment the old and replacement objects had next/match values of 200/100 and 300/250. The first table also shows the RPC age immediately after re-registration, when the two timestamps were about 120 and 30 seconds old. Per-supplier call counters identified which timestamp each gauge read.
What CoroPerf showed
On stock 3.3.1, Dropwizard’s getOrAdd returned the existing match gauge (segment 37). Reading it after plum executed getMatchIndex on the original FollowerInfo, JDI object 4466, and returned 2 (segments 81 and 82). The replacement appender used object 4959. The next-index and last-RPC getters also ran on the original object. PR #1587 changed addFollowerGauges to remove each metric by name and then register its replacement in the add path. In the landed capture the match name was removed in segment 64, getOrAdd returned a new gauge in 65, and its getter on the replacement object returned 8 in 110. The timestamp getter supplies the elapsed-milliseconds gauge. An aging timestamp can yield a rising reading even after its original appender stops. After orderly shutdown the 36 peer log segments from the 12 uninstrumented clusters contained exact copies of all 144 client-entry receipts. The independent decoder checked each frame’s CRC32C. A second pass using Ratis’s own SegmentedRaftLogInputStream matched the same bytes to their live receipts. For example, the release target’s 32-byte plum entry at index 7 starts at byte offset 249 in cluster/3.3.1/restart/trial-1/segments/s1/7146cff5-21e7-48a6-ba9b-62f859cb3a95/current/log_inprogress_0.
Scope and limits
The release run used the stock 3.3.1 Maven libraries. The two source comparisons used those same libraries with only LogAppenderMetrics compiled from the exact parent or merged commit. At the snapshot date 3.4.0 was the issue’s target and the latest published Maven release was 3.3.1. The landed JUnit regression supplied the executable two-object fixture. On the release and parent its first assertion stopped the test at next index 200, expected 300. The separate registry probe read all three gauges on every build. The cluster workload used three local gRPC peers in one JVM with separate log directories and an explicit restart of one appender. The reporter used Apache Ozone. JDI sampled executing Java methods, receiver identities and returns. These captures contribute zero coroutine origins.
