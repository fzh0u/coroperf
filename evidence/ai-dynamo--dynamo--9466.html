Issue findings

Local observation
For a 60,000-token request on a Tokio multi-thread runtime configured with one worker, the median time from notifying an unrelated ready Task to its first poll is 541–550 µs on the base and 3.33–3.45 µs with PR #9487's isolated block_in_place change. It runs before serialization completes in 0 of 300 base requests and 300 of 300 proposal requests. The JSON bytes and returned token counts match. For the same long requests the local completion time is 1.74–1.77 ms on the base and 1.79–1.85 ms with the change.
What CoroPerf showed
Both baseline observations have the same executable-address stack in an optimized ELF with the static symbol table and debug sections removed. The stripped instruction at ELF+0x1d54ac calls ELF+0x1c9ec0. The instruction at ELF+0x1c9f41 calls ELF+0x1c6710. Those destinations match the adjacent unwound frames. The address-only stacks are joined to two different launchers by matching the running Tokio Task ID to its original JoinHandle. The JSON body, control envelope and header agree on each request ID, including when the launch order and prompt sizes are swapped. Function labels come from the byte-identical code in the retained symbolized build.
Scope and limits
The replay isolates JSON serialization in the pinned AddressedPushRouter, with a local request receiver and a real loopback TCP response stream. Timing runs disable stack collection. The current-thread control retains inline execution and the ready Task runs later in both arms. The experiment measures local scheduling and leaves the reported multi-replica throughput outside scope. The issue is open and PR #9487 closed without merging. The inspected main has a later codec-aware envelope builder which still encodes the JSON fallback inline.
