Issue findings

Local observation
Two concurrent benchmark runs each receive one valid stream and one rejection with HTTP 200 headers. The reported revision and pinned main count four successes and 21 generated tokens in total. With PR #50427, both the pinned PR head and its change applied to main count two successes and five tokens. Both valid outputs are preserved, and both rejected requests keep the original error message with zero output tokens.
What CoroPerf showed
The two rejected requests send identical payloads and return through the same async_request_sglang_generate frames on one event-loop thread. The live request Task and exact RequestFuncInput connect each execution to its creation in benchmark. The parent Task joins those creation stacks to launch_evaluation and launch_calibration. The exact returned RequestFuncOutput also matches the object passed into each run's metrics. Stock asyncio debug records the shared spawn site and omits the launchers. The joins hold in both launch orders.
Scope and limits
The comparison runs the actual Python benchmark and HTTP client against a deterministic loopback service, using prepared inputs and a fixture tokenizer. It measures the benchmark's throughput numerator and success accounting. A model server and model tokenization are outside the comparison. The issue and proposed PR are open.
