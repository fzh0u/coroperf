Issue findings

Local observation
The five-row query returned 6, 6, 6 for one group and 3, 3 for the other in DuckDB 1.5.0 and 1.5.1. With positive inputs, each group can reach its total only once. In a second query each invoice had a frame containing just itself. Invoice 1 was for 198 cents and returned its customer's total of 3,762 cents. All 412 invoices returned incorrect amounts.
What CoroPerf showed
The native stack reached WindowSelfJoinOptimizer::CanOptimize from OptimizeInternal. Both release CLIs read the same window boundaries. Version 1.5.1 accepted the running frame, and its plan grouped by customer and joined the total back to every row. Version 1.5.2 rejected it and retained the window operator. Disabling only this optimization on 1.5.1 also restored the row-specific results.
Scope and limits
The reporter used macOS ARM64. These four release CLIs ran on Linux x86_64 with one execution thread. The original frame leaves the order within a group unspecified. The verifier checks whether any order of those rows could produce the returned sums. The invoice data is the Chinook sample database. The native captures observe synchronous optimizer decisions.
