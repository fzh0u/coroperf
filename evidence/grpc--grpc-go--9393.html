Issue findings

Local observation
The original TCP health RPC shutdown example runs once with gRPC-Go v1.83.1, Go1.25.0 and WaitForHandlers(false). After the original 200ms+1s connection-drain sequence, Stop remains blocked for15.001s. Native goroutine227 waits in handlersWG.Wait at server.go1989; goroutine196 waits on s.mu.Lock at1959. Both dumps show Server [address]. Closing the original handler release channel ends both shutdown calls and the process exits0. Full preparation/build/run121.16s; an earlier duplicate-source compilation failure had no workload and is archived.
What CoroPerf showed
Both goroutines self-report their native runtime IDs; independent all-goroutine dumps match the runtime trace birth/wait/exit events. CoroPerf joins creation0 to wait1 for227, restoring beginGracefulShutdown, and creation3 to wait4 for196, restoring submitForcedStop. Neither outer helper appears in the corresponding current dump or wait stack. Native wait intervals are16.002s and15.001s. Standard runtime trace already contains the full creator stacks; CoroPerf provides the normalized identity joins and combined view. Exact source retains s.mu via defer while waiting for handlers, explaining the stall when read with the native stacks.
Scope and limits
Named helpers only split the existing two go submission expressions; no additional shutdown goroutine is introduced. These are harness entry names, not recovered unknown production names. The same Server reference is visible in native dumps, and mutex ownership is a source-backed inference, not a generic ancestry or dynamic lock-owner observation. This confirms a15-second bounded stall and normal original release cleanup, not infinite lifetime or the production15-minute duration. The issue already explains the mutex cause. One successful workload only; no replay, alternate deadline/version, extra RPC batch or fix experiment.
