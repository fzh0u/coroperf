Issue findings

Local observation
The Redis server returned ["21-0", [], []] on the first page of a 412-entry pending list. redis-py 4.3.3 returned [] to the application, leaving it without the next position. All 108 eligible invoices remained with the original consumer. On 4.3.4 the application reached the terminal cursor after 56 calls. Independent ownership checks found all 108 invoices with the replacement consumer.
What CoroPerf showed
The recorded RESP2 bytes contain the cursor before the result reaches the callback. In the asyncio client, StreamCommands.xautoclaim created the Redis.execute_command coroutine whose execution stack reaches Redis.parse_response and parse_xautoclaim. The old callback returned element 1 alone. The fixed callback formats the entries in that element and returns all three elements. Replacing only this callback on 4.3.3 recovered the 108 invoices and the three IDs removed from the stream.
Scope and limits
The reporter described the iterative operation. This workload supplies the stream entries, idle times and consumer groups, using the reported Redis and redis-py versions on Linux. The measurements cover normal full-entry calls. A separate JUSTID control returned only the message IDs on both releases.
