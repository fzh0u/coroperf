Issue findings

Local observation
The archived original SDK makes two loopback vector searches with equal 200 ms response holds. The reads serialize on the event-loop thread. The first downstream query starts after the second router task's read returns. In a matched unprofiled run the same two queries complete in about 416 ms before the change and 260 ms with the open proposal. Returned nodes agree.
What CoroPerf showed
The identical synchronous read stacks join at 31 → 28 and 38 → 29. The downstream observations separately join at 44 → 36 → 28 and 46 → 43 → 29. Record 36 already exists during the read in the other router Task. The other read accounts for about 202 ms of the first downstream Task's creation-to-entry interval. Both the Task identities and timestamp ordering are recorded.
Scope and limits
The archived run uses the reported SDK and a loopback relay with a controlled response hold. A fresh CPU-only regression checks the same one-line fix on the current router source. It lets a callback run before either retrieval finishes when the retriever implements asynchronous I/O. A retriever that inherits the synchronous base fallback still blocks. Both versions return the same tool results. The issue and proposal remain open.
