Issue findings

Local observation
Two raw AsyncLLM.generate requests use the actual Qwen2-VL image processor for one and three images. The affected revision runs both calls on the event loop. Merged PR #49608 runs both on a single renderer worker. Across seven warm trials per revision, the median delay of a callback queued just after launching the two requests is 30.3 ms before the change and 0.135 ms after. Both revisions produce identical prompt token IDs, image grid metadata and pixel tensors.
What CoroPerf showed
The two preprocessing observations have identical physical frames within each revision. Before the fix, the actual active Task connects the caption call 2 → 0 and the relevance call 3 → 1. After the fix, the same WorkItem seen at submission and execution connects 8 → 6 → 4 and 9 → 7 → 5. The joined stacks recover the application launcher that the worker stack omits, alongside the exact request ID observed inside InputProcessor.
Scope and limits
The replay uses pinned vLLM frontend Python code, the real Qwen2-VL tokenizer and image processor, and generated local images. A fixture replaces EngineCore at the request handoff and supplies a final response to the real output collector. Separate unprofiled trials measure callback delay. Already-rendered inputs serve as a correctness control. GPU utilization and model throughput remain outside the experiment.
