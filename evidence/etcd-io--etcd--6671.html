Issue findings

Local observation
The reporter wrote foo3, foo1 and foo2, then requested creation order without specifying a direction. etcd 3.0.12 and all three members on the fix parent returned foo1val first. The fixed servers returned foo3val first. Every member’s stored creation revisions placed foo3 first at revision 2, followed by foo1 at 3 and foo2 at 4. Explicit ascending order returned foo3val on every build.
What CoroPerf showed
The range backend received CREATE with the order field set to NONE. On the parent, the rows entered and left the sort branch in key order. On the fix, the backend selected ascending order and returned the rows in creation-revision order. Capture segments 0, 1, 2 and 3 follow one gRPC request goroutine from its creation through both observations to its exit. A separate replay of each member’s committed WAL and MVCC versions establishes the expected order.
Scope and limits
The original workload used one v3.0.12 member. The three-member clusters, overwrite, historical read and explicit sort directions are additional controls. The keys have distinct creation revisions. The stack capture covers the original read on member 0 of each observed three-member cluster. The debugger and baseline runs used the same server binaries.
