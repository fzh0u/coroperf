Issue findings

Local observation
On the base, whichever request starts second waits for the first model's entire load. The replay observes its pending Future in the replica-wide asyncio.Lock. With the patch in PR #65825, the median start delay is under 0.8 ms for each model, and the median overlap is 45.1 ms. The median time for the pair falls from 111.4 ms to 66.2 ms in both launch orders. An extra request for the same model receives the same model object and leaves the loader count at one for that model. Repeated warm requests return the same objects with no extra loads.
What CoroPerf showed
The two loader Tasks have identical execution stacks on the same event-loop thread. The actual Task in the replica's model-ID map joins sampled loaders 4 and 5 to Task creations 2 and 3. At each creation the active request Task joins that record again to the interactive or batch entry in records 0 and 1. Each request receives the exact model object produced by its matched loader. Asyncio debug reports the common spawn site and omits both launchers. Reversing the launch order preserves both matches and reverses the waiting request on the base.
Scope and limits
The component replay uses public @serve.multiplexed on Ray 2.59.0 with the pinned multiplex.py from each arm. It uses one in-process replica context, two model slots, and async model-load fixtures with 45 and 65 ms waits. Each configuration and launch order has one warm-up, five timed trials, and a separate trace. Real model weights, GPU transfers, and proxy traffic are outside the measurement. Three upstream tests pass on the proposal covering overlapping loads, one shared load per model ID, and the capacity limit. The issue and PR are open.
