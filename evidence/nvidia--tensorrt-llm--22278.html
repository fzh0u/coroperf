Issue findings

Local observation
For 1,024 items, the original store makes 1,025 passes and visits 525,824 historical rows, including the final recount. PR #22280 records 1,024 individual outcomes without those scans. Event-loop thread CPU from loopback submission to batch completion drops from 235–256 ms to 20.4–21.3 ms in the two run orders. Both runs return the same 930 successes and 94 synthetic item errors. The proposal publishes the results URL only after the batch ends.
What CoroPerf showed
The two worker samples have identical _recount execution stacks after their HTTP submitters have finished. The executing asyncio Task and exact batch record connect observation 8 to worker creation 1, and the active parent batch Task connects it to HTTP creation 0 for evaluation. The indexing path is 9 → 4 → 3. Both paths remain correct when the POST order is reversed. In the traced base, the two-item evaluation batch visits five historical rows and the four-item indexing batch visits fourteen.
Scope and limits
The experiment runs the pinned TensorRT-LLM batch store, protocol models and route methods over a real loopback HTTP server with a synthetic item runner. Timings use seven warmed trials per size and arm in each order, with stack collection disabled. The 1,024-item pass counts come from a separate instrumented run. Cancellation keeps the same final results. The proposal passes all 30 upstream tests. Two new assertions fail on the base. GPU inference is outside scope. The current main batch store matches the PR base file, and the tracker and PR are open.
