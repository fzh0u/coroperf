Issue findings

Local observation
On the default v0.29.0 single-worker executor, the thumbnail begins 19.8 ms after submission in the traced CPU run, after the document renderer returns. Reversing launches moves the wait to the document. In two unprofiled follow-up runs with six 1275 × 1650 images per batch, the two-process medians are 202.0 and 181.1 ms when returning results by value, and 165.0 and 172.6 ms when using PyTorch shared tensors. The corresponding one-thread medians are 176.8 and 180.1 ms. The two-thread control is fastest at 97.3 and 94.6 ms. Prompt token IDs, image grids, and pixel tensors match.
What CoroPerf showed
Both samples have identical renderer stacks on the same worker thread. Matching each exact CPython WorkItem to the Task active at submission restores the document chain 4 → 2 → 0 and thumbnail chain 5 → 3 → 1. Their submit, start, and finish times then separate queue waiting from work inside the renderer.
Scope and limits
The fixture uses the pinned CPU renderer with Qwen2-VL processing files and one local image per prompt. The multimodal and prefix caches are disabled. Each median uses seven warm trials with one intra-op thread. The large page tensor has 12.77 MB of pixels. The prototype uses shared storage for output tensors while both modes transfer decoded input images. In the separate mixed-size control, both process transports are slower than one thread. The B300 workload and GIL explanation remain unverified, and the issue is open.
