Issue findings

Local observation
The reporter requested an embedding for “hello”. LitServe 0.2.18 returned HTTP 200 and [5.0, -0.5, 0.25]. Release 0.2.19 returned “AACgQAAAAL8AAIA+”, the three little-endian float32 values encoded as a string. Each release served 31 requests per batch. All 14 base64 requests received the wrong JSON type on 0.2.18 and the correct type on 0.2.19. All 17 other requests passed on both. OpenAI Python 1.109.1 exposed the list to callers explicitly requesting base64 on the old release. Its default path requested base64 and delivered numeric lists on both. The reporter’s unchanged suite produced six failures and eight passes on 0.2.18, then 14 passes on 0.2.19.
What CoroPerf showed
Two simultaneous clients sent “hi” and “hello” over distinct loopback connections. A single CPU prediction handled both. Each received the correct numerical vector. On the fixed release only the base64 client received a string. CPython observed FastAPI creating the native endpoint coroutine before its first await. The identical coroutine and physical frame returned the affected response. On the fixed request the same frame called b64encode with the exact packed bytes. The model worker ran synchronously in another process and supplied ordinary floats on both releases. The two transport controls used multiprocessing and ZeroMQ. A second complete batch reproduced every response body.
Scope and limits
The reporter supplied a deterministic three-coordinate CPU fixture. An additional workload used six original pretrained GloVe vocabulary rows to embed three two-word phrases. Independent rational averaging verified every one of 1,050 returned float32 components per release per batch. The complete fix parent and fix also served the reporter workload and matched the corresponding release byte for byte. The measured coroutine origin belongs to the HTTP endpoint. Synchronous worker prediction and response packing have their own physical samples.
