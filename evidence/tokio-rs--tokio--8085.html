What stitching revealed

Issue findings

Local observation
In the stock Tokio 1.54.1 control, six Unix-socket reads on the shared runtime waited a median of 107.924 ms after the peer began writing. Moving the same 120 ms CPU poll to a separate runtime gave a median of 0.039 ms on six reads.
What CoroPerf showed
Both launch paths had identical physical function stacks after suspension and the same built-in TaskMeta spawn location. CoroPerf assigned each hot stack to the active Tokio task by its observed poll interval. The creation stack recovered launch_profile or launch_inventory in all 24 verified observations across two batches, including reversed-order runs. The stack snapshots carried neither a task ID nor a phase label.
Scope and limits
This is a local, bounded adaptation of the scheduling issue with one asynchronous I/O worker and controlled CPU slices. Read delay is a socket readiness-to-read proxy. The experiment compares two runtime layouts.
