What stitching revealed

The same scheduler stack completes tools for two distinct requests. Matching the scheduled callback and the batch carried by Spring AI's ToolContext restores each registration and application launcher, so each serial tool sequence is attributed to its own request.

Issue findings

Local observation
Three local tools have delays of 120, 80 and 40 ms. Both the original manager and the async proposal with concatMap complete the batch in about 242 ms, with one active tool at a time. An opt-in local patch reduces the median to about 162 ms with two active tools and 121 ms with three. The callbacks finish out of order, and the tool results retain their original IDs, payloads and order in the model conversation.
What CoroPerf showed
Two overview callbacks have identical execution stacks on one Reactor scheduler thread. Matching the exact scheduled Runnable and its Mono sink restores each registration stack. The original Batch object passed through Spring AI's ToolContext leads back to the respective application launcher. The catalog path is 4 to 2 to 0 and the research path is 6 to 3 to 1. Reversing launches swaps the request attribution.
Scope and limits
The replay compiles the actual parent and PR #4756 tool managers against Spring AI Model 1.1.0 dependencies. The responses and delays are synthetic. The local patch applies to the PR checkout and opts explicitly into overlapping independent tools. The provider streaming path and current main-branch decisions API remain outside the runtime test. Both the issue and PR are open.
