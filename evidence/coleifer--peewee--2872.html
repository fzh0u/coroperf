Issue findings

Local observation
Peewee 3.17.2 returned False when the reporter tested a freshly executed cursor. Iterating that same cursor returned all 42 IDs. When the reporter called list(cursor) first, the truth test returned True. A separate empty result also evaluated as True after iteration. The immediate fix and release 3.17.3 returned True for the 42-row result and False for the empty result at both points.
What CoroPerf showed
The physical trace links the wrapper returned by SelectBase._execute to the receiver of the actual truth test. In 3.17.2 the __bool__ method read populated. It was false before the first fetch and true once iteration reached the end, including for the empty cursor. The fixing commit removed that method. Python then called the existing __len__, which filled the cache and returned the row count. Direct psql reads on separate connections confirmed every row ID before and after each trial.
Scope and limits
The reporter supplied two code blocks and observations in comments. The harness supplied the model, 42 committed rows and the public bool(cursor) call. Every locking SELECT ran on a real, private PostgreSQL 10.23 server. The two trials used the release that is also the fix parent, the fixing source commit and the next release. The six captures observed synchronous calls and returns. All three builds yielded the full rows during iteration. Matched coroutine origins total zero.
