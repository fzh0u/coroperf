Issue findings

Local observation
The original JavaScript calls created a table on a single elected leader. A local read allowing up to 100 hours of staleness returned HTTP 200 with a stale-read error. After two voters joined and the cluster committed a fourth row, both followers returned all four rows under the same bound. The old leader still rejected the read.
What CoroPerf showed
The Go runtime recorded Store.Query taking its stale-read return path on the leader. The saved last-contact time was January 1 of year 1. The elapsed duration saturated at the largest signed 64-bit value and exceeded the 100-hour limit. The trace links this exact request to the HTTP connection goroutine started by net/http.(*Server).Serve. The fix applies the contact check only on followers.
Scope and limits
The replay used the reporter’s source commit and Go 1.18.2 on Linux amd64. The original ran on Windows. Seven runs compared ordinary and traced servers, including the parent, fix and two releases. The database backup contained the same four rows that the cluster returned. Both followers still enforced a one-nanosecond limit after the fix.
