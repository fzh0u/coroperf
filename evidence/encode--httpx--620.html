Issue findings

Local observation
The reporter passed json= with an explicit Content-Type. On a local GeoJSON POST, HTTPX 0.9.3, 0.9.4 and the fix parent sent application/json. The merged fix and 0.9.5 sent application/geo+json. All 30 GeoJSON requests returned HTTP 200 with the same 42-byte request body. In a separate Django JSON:API application, the affected explicit POST received HTTP 415 and inserted zero rows. The repaired POST received HTTP 201 and inserted one row, verified by a subsequent GET and by reopening SQLite.
What CoroPerf showed
HTTPX computed application/json as the encoder default. On the parent, the synchronous Request constructor assigned it over the caller’s header. The one-line fix used setdefault. The captured Client.request coroutine was observed before its first await inside httpx.api.request. Its same running frame was present before and after header selection, and again in h11.write_request. HTTPX created Client.send after the decision. Its argument was the same Request object, and its running frame was present at serialization. The server received the media type observed at the writer.
Scope and limits
The original report omitted a payload and media type. GeoJSON supplies the local header example. The independent consumer uses the JSON:API media type and the packaged rest_framework_json_api.parsers.JSONParser from version 7.1.0. Its evidence records the WSGI input, parser selection, response documents, subsequent listing and committed rows. These HTTPX releases named the async client Client. Coroutine object and frame identities are scoped to each process.
