Issue findings

Local observation
On aiohttp 3.9.1, a GET for a precompressed file with dynamic compression enabled advertised deflate. Decoding the response once left 38 bytes of gzip data. The fixed server advertised gzip and returned the original 18 bytes after one decode. Serving the precompressed file alone and enabling compression on a plain file both produced the expected contents.
What CoroPerf showed
RequestHandler.start created the task that selected the gzip file. In that same request, _do_start_compression selected deflate. The client port, request object and task identity connect that decision to the raw HTTP response. Repeating the request with a second TCP client and a byte-identical file confirmed the result.
Scope and limits
The reported release ran locally on Python 3.12.13. The report used 3.12.0. The parent and fix ran with aiohttp’s Python implementation. The reporter’s test explicitly expects the old deflate header, so its assertion fails on the corrected header. A separate check decodes and compares the complete body.
