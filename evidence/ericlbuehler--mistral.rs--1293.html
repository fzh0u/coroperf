What stitching revealed

Start with the observed execution stack. Follow the joins back to the creation stack and earlier callers. Each block keeps its recorded frame order.

Issue findings

Local observation
With two loaded models and no requests, each scheduler thread consumes approximately one CPU core during the 900 ms idle window. In the revision with merged PR #1655, the idle engine awaits its request channel and neither thread advances by one 10 ms CPU tick. A short chat request to each model completes after the idle window in both builds.
What CoroPerf showed
The two idle stacks show the same Engine::run future and Tokio runtime frames. The actual future creation on the native engine thread also has the same library frames in both cases. The engine token passed through the spawning closure links those records back to the distinct application launch stacks. The catalog is 2 → 1 → 0 and search is 5 → 4 → 3. Reversing model construction reverses the attributions.
Scope and limits
This test embeds the Mistral.rs Rust API and runs two copies of a one-layer CPU model. It compares the merge parent d101c5fce7ee1 with merged revision 65faf59df395. The earlier logger loop and the original production server are outside the comparison. The per-thread counters measure the idle window. The stack probes collect the first idle execution before that window.
