Issue findings

Local observation
One reported silent-loopback connect/shutdown scenario with psycopg3.3.9, psycopg-pool3.3.3 and CPython3.12.16 accepts one connection. At0.604s after startup, asyncio.run is still in _cancel_all_tasks; worker0 is unfinished with cancelling()=1 at pool_async.py:679 awaiting q.get. Other pool workers are cancelled. Preparation and the sole run take76.80s. The diagnostic callback saves evidence and exits the process0.
What CoroPerf showed
The actual Task address0x79ac9a18c100 independently matches asyncio.all_tasks, the pool-held worker reference and the generic CoroPerf creation/sample records. CoroPerf recovers start_connection_pool from the worker creation stack, absent from its later native/current wait stack and unavailable in native debug creation traces. The same worker has a scoped CancelledError observation in _connect/_add_connection before returning to queue wait. The focused capture has30 attributed observations; the catalogue highlights one cancellation observation and the last wait snapshot. The source report already describes cancellation swallowing; the added fact is historical application ownership.
Scope and limits
This proves a bounded shutdown stall, not infinite duration. asyncio.run does not return normally: the observer calls os._exit(0), closing owned loopback sockets. No pool.close workaround, fix, extra cancellation, reset path, other version or replay was tested. start_connection_pool is a submission helper introduced in this standalone harness. No exception-object identity was captured, so propagation records are not counted as distinct errors. A file-scoped exception probe supplements generic Task birth/sample capture; the original graph is preserved and the focused graph selects only the independently identified worker, without synthesizing runtime events.
