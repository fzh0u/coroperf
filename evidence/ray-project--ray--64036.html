Issue findings

Local observation
Four requests enter one live Serve replica with an initial limit of two batches. Changing user_config to one leaves the base implementation's fixed semaphore at two. With PR #64040, the two active batches finish without interruption. The next batch starts when both drain. Raising the limit back to two starts the last batch while the third is still active. Each run keeps the same replica PID across its updates and returns all four expected results.
What CoroPerf showed
Each handler uses the same physical function stack. Live Task and coroutine identity match the handler observations to their own creations. The retained _SingleRequest and its exact Future then join each creation back to the corresponding enqueue. This identifies the two waiting batches as the already-enqueued second caption request and second embeddings request, and verifies which one enters after each limit change.
Scope and limits
The control and proposal use their pinned batching modules with the same Ray 2.59.0 runtime and AnyIO 4.16.0. A declarative user_config update calls the deployment's asynchronous reconfigure method. The fixture uses one replica, one item per batch, and controlled release points. It checks admission and results with outstanding work. GPU throughput and other deployment topologies remain outside the experiment. Both the issue and PR are open.
