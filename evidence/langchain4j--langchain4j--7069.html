Issue findings

Local observation
Two custom exception mappers throw on a worker. On main, both caller Futures remain pending after the worker finishes. The mapper failures are visible in the dependent stages returned by whenComplete. With PR #7070 applied, each caller Future completes exceptionally with its own mapper's exact throwable after just one attempt. The already-failed input case gives the same before-and-after result.
What CoroPerf showed
The two mapper executions have identical physical stacks. The completion callback carries the exact caller Future previously observed at the first attempt. Matching JDI object IDs joins record 2 to the batch launch in record 1, and record 3 to the interactive launch in record 0. Reversing completion order swaps the recovered callers.
Scope and limits
The Java 17 fixture supplies both failed attempts and explicitly throwing custom mappers. The traced retry sources are from main 8705b925d715 and the same revision with the production change from open PR #7070. All 24 tests from the PR pass with that change. Four mapper-failure tests fail on main. The issue remains open.
