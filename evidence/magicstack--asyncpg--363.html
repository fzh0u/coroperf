Issue findings

Local observation
The reporter queried 1970-01-01 20:31:23.648000. PostgreSQL returned the correct bytes. On asyncpg 0.17.0 the application read 20:31:24.648000. The fix and release 0.18.0 returned the original timestamp. Two independent USGS earthquake times from 1989 and 1994 also gained one second in the affected builds. An interval of minus one microsecond came back as positive 999,999 microseconds.
What CoroPerf showed
A native stack reached timestamp_decode from the PostgreSQL row decoder. For the posted value, the affected helper split −946,610,916,352,000 microseconds into −946,610,916 seconds and a positive remainder of 648,000 microseconds. That quotient was one second too large. The fixed helper rounded the quotient down to −946,610,917 and kept the same remainder. A separate coroutine capture linked the main task created in the reporter’s script to fetchval returning the shifted time.
Scope and limits
The original Python 3.6.5 program ran against local PostgreSQL 10.23 with the connection port substituted. The report used PostgreSQL 10.3. The published wheel supplied the native decoder stack. Debug builds at the parent and fixing commits supplied the local integer values. The protocol callback and the application task were captured in separate runs.
