Issue findings

Local observation
A 32-request backlog alternates 160-token catalog inputs with 16-token search inputs. FIFO uses 5,120 padded token positions. Sorting fixed windows of 16 uses 2,816 across the same eight batches of four. On the CPU Candle fixture, median backlog drain time over eight trials per arm is 1,234.4 ms for FIFO and 719.8 ms for sorting. The first catalog request finishes later, at median 200.6 versus 237.7 ms. The largest absolute embedding difference is below 5.37e-7.
What CoroPerf showed
Records 1 and 3 have the same physical embedding-resume stack on one Tokio worker. Each running Task matches the JoinHandle captured at its own launch, and the request metadata carries that Task ID to backend dispatch. This joins record 1 to catalog ingestion and record 3 to interactive search. In the FIFO capture these two requests share a batch padded to 160 tokens per input. The sorted capture groups the search request with other 16-token inputs.
Scope and limits
A fixture holds the batching task until all 32 requests arrive. Stack collection is off during timing. The loopback HTTP check validates embeddings and the opt-in on the real router. The performance comparison covers this CPU model and controlled backlog. The patch keeps FIFO as the default and only sorts complete windows for padded backends. The issue remains open.
