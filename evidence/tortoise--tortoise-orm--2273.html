Issue findings

Local observation
On SQLite in WAL mode, creating a model with the reported local time of 09:00 and reading it back returned 09:00 in every build. In 1.1.8, assigning that same naive time to an existing model and saving it returned 17:00. A QuerySet update also returned 17:00. Both operations returned 09:00 after the fix. On insertion, automatic timestamps used a UTC offset in the old build and the Shanghai offset in the fixed build. Both represented the correct instant.
What CoroPerf showed
The creation path converted the input to a Python field value first and attached the configured Shanghai zone. The update path entered DatetimeField.to_db_value with a naive value and called make_aware with UTC. The SQL executed by SQLite contained 09:00+00:00, which became 17:00 on reload in Shanghai. The fix attached the configured zone during writes. In the hourly meter import, the creation stack and the make_aware sample identify the specific task that wrote the naive timestamps.
Scope and limits
The issue supplied a timestamp, configuration and steps. The local program implemented those steps on CPython 3.11 and SQLite WAL. The supplementary import used German load readings from two weeks spanning both 2019 clock changes. The published UTC column distinguishes the two occurrences of 02:00 on October 27. With the fixed build, dropping that distinction still misplaced one reading. Preserving the Python fold flag or supplying an explicit UTC offset recovered all 336 instants. The matched child task belongs to this local import.
