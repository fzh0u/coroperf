Issue findings

Local observation
With adaptive batching enabled, the original HTTP program received status 200 and one INT64 class label (8) from MLServer 1.0.1. Turning batching off returned all ten probabilities for the same digit. In a separate measurement, ten HTTP requests with distinct IDs reached the model as one 10 × 64 input. Version 1.0.1 returned ten labels. The merged fix returned a 10 × 10 probability matrix. We matched each split response to its HTTP request ID and checked every value by independently walking the 100 fitted trees.
What CoroPerf showed
The HTTP handler and queue both received predict_proba. The task created in AdaptiveBatcher._start_batcher_if_needed reached BatchedRequests._merge_requests, which returned a request with no output selection. The batcher created a second task to run the model. Its stack reached ForestClassifier.predict on the affected build and ForestClassifier.predict_proba after the fix. Both creation sites were matched to the executing coroutine and frame.
Scope and limits
The reporter supplied the client code and described a random forest. We trained a seeded forest using the tutorial’s handwritten digits and train/test split. This accounts for the different example label. The traced service ran inference in-process. Stock runs with the default worker settings reproduced both release outcomes. The fix restored probability output while the batched response still omitted model_version. The 1.1.0 stable release returned v0.1.0 in that field.
