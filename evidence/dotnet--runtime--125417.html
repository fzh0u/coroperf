Issue findings

Local observation
In the draft CoreCLR async-stack mode, a direct await displays Program.DirectOuter. Through the synchronous Task forwarders, both resumed stacks show Program.Callee as the only application method. TPL payloads carry task IDs and the same operation name. The stock dotnet-trace Speedscope view and task-aware TraceEvent worker stacks also omit both launchers.
What CoroPerf showed
CoroPerf captures the physical stack at TraceOperationBegin. The unlabeled worker sample is assigned to the active TPL Execution interval on its thread, then joined to the creation record for the same Task ID. In the displayed run Task 4 spans records 4–8 and joins observation 5 to LaunchInventory at creation 2. Task 1 spans records 9–13 and joins observation 10 to LaunchProfile at creation 0. All eight observations match independent Task IDs and post-await checkpoints across both launch orders.
Scope and limits
A controlled two-caller extension of the upstream synchronous-forwarder example, on Linux x64 with draft CoreCLR commit 7e2cfb7b13b5. The runtime emits the TPL creation and execution events used here. The profile control uses dotnet-trace 10.0.750501 and TraceEvent 3.1.23, with a brief post-await sampling window.
