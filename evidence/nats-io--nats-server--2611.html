Issue findings

Local observation
NATS Server 2.6.1 reported 237 pending messages for an ephemeral consumer configured to deliver the latest message per subject. Reading all 250 stream sequences independently found 248 retained records and exactly 40 subjects. The consumer received and acknowledged precisely those 40 latest records. Its final ACK still reported 197 pending. A separate pull consumer returned 404 No Messages with the same count.
What CoroPerf showed
The consumer initialization stack reaches setInitialPendingAndStart. With a filter identical to the stream subject, the affected branch used 248 retained messages minus the 11 sequences before the first selected record. The native trace then shows that same request goroutine launching the delivery worker in setLeader. All 41 reply subjects encoded in deliverMsg match the receiving client byte for byte. The fix counts the 40 selected sequences and reaches zero after the last historical delivery.
Scope and limits
The deterministic key history reconstructs the public counts. The original application data was unavailable. Stock releases establish the behavior with file and memory storage. The function stacks and intermediate values come from observed builds of the upstream fix and its direct parent. The upstream four-key regression also reproduced the opposite error on a different history: two pending instead of four.
