Issue findings

Local observation
The reporter published four records in one partition and batch with timestamps 0, 10, 10 and 20 milliseconds after a common base. At +5 ms, the affected service returned offset 0, whose record was too early. At +10 ms, it returned offset 2, skipping the first record with that timestamp. A consumer sought to each returned offset and read those records. The fix and Apache Kafka 2.2.1 returned offset 1 and the +10 ms record for both queries.
What CoroPerf showed
The Kafka contract selects the earliest offset whose timestamp reaches the request. The parent scanned the whole batch and updated its answer whenever a record timestamp was less than or equal to the request. At +10 ms this selected offset 1 and then overwrote it with offset 2. The fixed scan stopped at offset 1. The Go runtime recorded the creation of the service event loop in NewCluster. The same goroutine handled the sampled requests, and the peer, correlation ID, query and result match the captured Kafka exchanges.
Scope and limits
The literal reporter test ran on Linux/amd64 with the reported Go 1.26.1. The six paired runs used a topic-specific client, uncompressed records and the Kafka 2.2 protocol cap. The singleton-batch topic and seven extra lookup times are local controls. The +21 ms wire reply had offset and timestamp −1. The admin client then looked up the partition end and returned offset 4. The goroutine evidence covers the two traced kfake runs. Apache Kafka supplies the independent broker and on-disk readback.
