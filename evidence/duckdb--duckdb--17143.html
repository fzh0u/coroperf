Issue findings

Local observation
The reporter inserted abc with count 20, then upserted the same name with count 30. On DuckDB 1.2.2 and 1.3.2, the second statement returned ID 2 while the reopened table contained just (1, abc, 30). DuckDB 1.4.0 and a live PostgreSQL 14.13 server returned ID 1 and persisted the same row. All four engines advanced the sequence to 2. The posted programs and the on-disk comparison repeated in independent batches.
What CoroPerf showed
The conflicting insert generated candidate ID 2. GDB observed that value at the return instruction of the sequence function in all three release wheels. On the affected releases, the conflict handler built its return row from the proposed insert and replaced the count. The output collection received a dictionary vector whose selected BIGINT was 2. On 1.4.0 the same SQL ran through the merge and update operators, and the output collection received a flat BIGINT of 1. The native values agree with the unsampled client results.
Scope and limits
A separate DuckDB application used the upsert result as a foreign key for a receipt. On both affected releases ID 2 found zero stations, the database rejected the receipt, and rollback left Fairbanks at count 20 with zero receipts. DuckDB 1.4.0 committed count 30 and one receipt. Reading the key by unique name worked on all three releases, as did inserting a new name. All 18 original transaction databases were reopened and checked. The PostgreSQL comparison covers the reporter’s original workload with two LONG spellings changed to BIGINT. The report spells the affected version “1.22”. The tested releases establish the operator change, while the first corrected commit remains unbisected. The native stacks establish synchronous execution only.
