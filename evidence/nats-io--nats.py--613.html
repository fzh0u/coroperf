Issue findings

Local observation
The reporter requested stream-test.consume3 when creating a durable push consumer. With nats-py 2.9.0, the broker stored a generated inbox as the delivery subject. The returned JetStream subscription received all ten binary records. An independent Core NATS subscription on the requested subject received zero. The landed fix and the first fixed release delivered all ten records to both subscribers. Explicit consumer creation through the manager and automatic inbox allocation when no subject was supplied both worked across all four builds.
What CoroPerf showed
The caller’s creation stack points to the original line awaiting js.subscribe. The same live JetStreamContext.subscribe frame allocated an inbox and assigned it to config.deliver_subject while creating the consumer. The next sample shows the new value on the caller’s config object. The outgoing request, broker reply and underlying subscription agree on that inbox. The fix checks whether the caller supplied a subject before allocating one. A separate experiment restarted the broker and rebound the stored durable with either client version. Each new client used the subject the first client had saved.
Scope and limits
The report supplies a coroutine and consumer settings. The harness supplies the stream, missing imports, callback and payloads, connects to an ephemeral loopback port, and cancels the final sleep after delivery. All tests use the reported server release, 2.10.21. The three-message trace is an independent execution of the original coroutine. The restart experiment publishes one additional record per stage.
