Issue findings

Local observation
With timestamped backups enabled, a three-voter rqlite 8.26.6 cluster uploaded two database snapshots exactly 300 seconds apart under the same object name. The object store assigned distinct versions. Downloading and opening them with SQLite showed one committed row in the first snapshot and two in the second. Version 8.26.7 wrote two distinct timestamped names over the same interval.
What CoroPerf showed
The Go runtime traced the periodic worker to Uploader.Start. Its stack enters S3Client.Upload and TimestampedPath. On the fix parent, the worker supplied exactly the same timestamp on three successive calls even as the database index and object write time advanced. The old client bound the UTC method to the first time value. The fix reads the clock on each invocation.
Scope and limits
The test used a local three-voter cluster and a versioned S3-compatible VersityGW service. Both release builds ran at the reported five-minute interval. The recording builds used a four-second interval so three timestamp arguments could be compared on the same goroutine.
