Issue findings

Local observation
The reporter set the index to b = [3, 1, 3] across two partitions, sorted by a, and asked for the length. Dask 2023.9.0 and the fix parent returned 0 in both trials. Computing the rows separately returned an empty frame. The fix and 2023.9.1 returned all three (a, b-index) pairs in order. Both a direct sort of the input and pandas gave (1, 3), (2, 1), (3, 3). Each build also returned three rows with the reporter’s ordered keys, unique keys and one-partition controls.
What CoroPerf showed
Both workers’ saved Arrow files together contained all three rows. The affected workers wrote files named 0.0 and 1.0. The output coroutines asked for 0 and 1, handled the lookup misses, and returned empty partitions. On 2023.9.1 the filenames matched and the reads returned both partitions. For partition 0 the runtime links creation in distributed.utils.sync (segment 16) to the disk read (22) by the same task and coroutine frame. The metadata was built earlier on the driver. In rearrange_by_divisions the example index was [1, 2]. The affected partition metadata used [0] and the assigned column was float64. The fix aligned it to [1] and the column stayed int64. Applying the landed index assignment in both metadata builders on the old release restored three rows. Removing it from both on the newer release triggered the integer-column check while planning the final shuffle.
Scope and limits
The posted length and the ordered rows came from separate evaluations on the same indexed frame. Worker disk traces cover the two releases. The paired Dask source runs held distributed at 2023.9.0. The matched coroutine explains the empty partition returned by the worker. The link to the driver’s metadata decision comes from comparing the driver measurements, landed source and separate alignment experiment across runs. Both landed dtype tests failed on the affected builds and passed on the corrected builds. The task-shuffle and fractional-index controls each returned three rows in all four alignment runs. The second table uses a separate synthetic input of eight records totaling 44 units. Units are summed from the rows each computation actually returned.
