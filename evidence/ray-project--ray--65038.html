Issue findings

Local observation
In the Ray 2.56.1 planner replay the first chunk reaches the consumer after its producer yields all 12 chunks. With the local patch it arrives after one yield. A separate single-node map_batches memory check measures the actor’s live Arrow pool at each yield. At 4 and 24 one-MiB chunks, the stock async path peaks at about 4 and 24 MiB above entry, respectively. The patched async path peaks at about 4 MiB in both cases. All output bytes and row order match.
What CoroPerf showed
The first-yield stacks share the same async generator and planner frames. The live Task object connects observation 3 to the first input at Task creation record 0, and observation 2 to the second input at creation record 1. The event order shows that the first delivery waits for its own producer's list to complete while the other producer is already running.
Scope and limits
The memory check uses one actor and one input batch per run, a 512 KiB target block size, and one oversized row per output block. The metric covers live allocations in the actor’s Arrow pool at the yield points. The local candidate also preserves all 36 rows in a separate actor-retry check. Process RSS, object-store memory, worker restarts, and multi-node throughput remain unmeasured.
