Issue findings

Local observation
The opt-in backend's first draft waits synchronously for each worker result in the tested SGLang path. The worker-pool draft awaits it. Both variants use the same two-worker CPU pool and route both fixture sessions to their respective home workers. The prompt token IDs match the full reference encode. In seven unprofiled warm trials, the median delay of a callback queued after both request launches is 1.37 ms on the first draft and 0.139 ms on the worker-pool draft.
What CoroPerf showed
Both results reach the same collector thread and physical Scheduler._finish stack. The exact callback object connects the first draft's results along 3 → 2 → 0 and 5 → 4 → 1. The draft with awaiting connects 10 → 8 → 6 and 11 → 9 → 7. In that version the callback closes over the actual Future, and _set_result delivers the same result object to that Future. This verifies which requester received each result without treating the collector thread as the owner.
Scope and limits
The fixture uses pinned SGLang tokenizer methods, TokTier 0.3.0, two real local worker processes, and two synthetic Qwen3 sessions. It measures event-loop callback delay and checks token parity. Full server startup, GPU time to first token, and broader tokenizer configurations remain outside the fixture. The RFC is open. Worker-pool draft PR #44382 closed before merge.
