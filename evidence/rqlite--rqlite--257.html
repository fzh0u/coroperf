Issue findings

Local observation
The maintainer’s common table expression should return one row containing x = 1. The v8.43.3 shell printed 3, 0 or 2 affected rows, depending on the preceding write. Across three voters we found all three reads in the replicated log. The v8.43.4 shell returned the expected row each time and the reads added no entries. Switching only the client changed the outcome on either server release.
What CoroPerf showed
Four Go stack samples follow the shell from its WITH dispatch into executeWithClient, through the actual endpoint and into the affected-row display. The older CLI sent the read to /db/execute. Its response contained the same change count that SQLite retained after the preceding write. The repaired requestWithClient selected the table display using the columns and values returned by /db/request. A recursive read of eight Chinook employees showed the same routing difference. A recursive INSERT committed all eight employees on both releases.
Scope and limits
The 2017 report omitted the version. The stock v3.9.2 CLI has the same source tree as the shell on the reporting date. On its matching daemon it printed one affected row for both a one-row result and an empty result. The later maintainer report and fix supply the SQL for the three-node comparison. The main comparison uses adjacent 2025 releases, with official client binaries, a local three-voter cluster and a separate line-preserving stack observation build. The stack samples track synchronous work on the CLI main goroutine.
