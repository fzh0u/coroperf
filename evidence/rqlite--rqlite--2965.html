Issue findings

Local observation
The posted INSERT combined CURRENT_TIMESTAMP and strftime in two DATETIME columns. The reported release acknowledged one inserted row, but the first column stored the text CURRENT_TIMESTAMP. Its typed API value was 0001-01-01T00:00:00Z and its Unix epoch was NULL. All three healthy voters in the parent cluster returned those values. At the fixed revision in UTC, all three returned a timestamp matching the HTTP response clock.
What CoroPerf showed
The parent parser classified CURRENT_TIMESTAMP as an identifier. Visiting strftime marked the statement for serialization, which put double quotes around the identifier. SQLite accepted that unbound quoted name as text. The fix recognized a timestamp literal and emitted datetime with a numeric Julian day. The HTTP peer, Go creation event, visitor stack and returned Raft index identify one request goroutine. All three Bolt stores contain the same replicated command bytes for that index. Local backups independently confirm the resulting value.
Scope and limits
The six posted curl requests use loopback port remapping and one fresh connection each. The three-voter runs, parameterized insert, Unix-epoch reads and timezone comparison are local controls. Each process run has its own wall-clock timestamp. UTC results are checked against that request’s time window. With the fixed server explicitly set to Asia/Shanghai, the mixed insert returned an epoch 28,800 seconds ahead of its HTTP Date in this run. The origin evidence identifies the leader’s HTTP connection goroutine.
