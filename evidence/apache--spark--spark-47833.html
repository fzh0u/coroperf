Issue findings

Local observation
The direct DataSource path-check replay loses the application caller on Spark 3.5.1 and recovers it with the existing helper on 4.1.1. In the asynchronous application extension, both releases report the same missing local file from two otherwise identical worker stacks. The 4.1.1 helper reaches the shared application task but omits both historical launchers. Existing-file controls return the expected single path.
What CoroPerf showed
Capture the actual FutureTask submitted by each launcher. When the application worker submits a Scala Future, its executing FutureTask is the same recorded object. Match the callable passed to Future.apply to the same live callable in the error stack, and bind it to the returned Future. These two object relationships recover the interactive and batch entries from identical creation and execution stacks. A separate catch observer checks the exact returned Throwable against the original task owner. Across two batches, both launch orders and both releases, all 16 historical callers match.
Scope and limits
This is a local-file component replay of the public DataSource API, plus an explicitly separate application-executor extension. It does not run the reporter's private HDFS job. The ordinary exception and selected JFR exception/thread-ancestry controls omit the historical entry in the extension. Stock 4.1.1 already solves the direct-call endpoint. Removing the Future binding, historical creation or parent-task relation prevents recovery of the original entry. Missing-path errors remain expected input failures; CoroPerf restores their caller context.
