Issue findings

Local observation
With 512 MiB of host KV storage on one A100, worker registration takes a median of 126.5–143.6 ms on the base and 123.6–124.4 ms on the draft's synchronous path. With the draft's async option it returns in about 0.10 ms. The worker becomes ready 129.4–134.2 ms after entry when polling begins immediately. An independent GPU reduction completes before readiness in all ten async trials, and both ends of the host buffer pass the real DMA round trip. At 1 GiB in the loopback service, the async draft's first HTTP completion arrives 279 ms before the connector-ready log with eager execution and 292 ms before it with CUDA graph capture. In the graph run, host registration starts after capture finishes. All six service runs return the same completion text, finish reason, and count of four tokens.
What CoroPerf showed
The two background pin_tensor returns have identical frames on separate native threads. The actual Thread, AsyncHostBuffer and allocation callback join each pin to the construction scheduled in get_init_state. The active initialization Task connects that construction to launch_interactive or launch_batch. The same mapping holds when launch order is reversed.
Scope and limits
The worker component uses the pinned base and draft with actual CUDA registration and DMA. Its fixture provides the KV layout and bridges PyTorch device APIs. All 37 selected readiness and host-buffer tests pass in a separate CPU run. The loopback comparison uses a seeded tiny Llama, Triton attention, and the base revision's CUDA wheel files with each pinned Python tree. It runs each of the three connector configurations once per execution mode and measures the HTTP reply order relative to the worker readiness log. The issue and draft PR remain open.
