Issue findings

Local observation
A store that displayed node zero as Node[0] failed the public OpenRaft conformance suite on commit 548a449. The tenth check read the initial state of an empty store. It expected the string “0” for LogIO, Apply and Snapshot, while the store returned “Node[0]” for each. Substituting exactly those three labels made the full printed states identical. Formatting the same node type as a plain integer let the parent complete the entire suite. Commit 5863174 passed both formats. Each condition ran twice, with matching stock and debugger outcomes.
What CoroPerf showed
The storage helper formats the configured node type. The parent suite built its expectation by formatting a raw u64, and the derived equality operation included the three progress-label strings. PR 1660 converts the constant to the configured node type before formatting it. At the actual assertion, GDB inspected both operands and followed the physical stack through the individual check, run_test and test_store to the active Suite::test_all poll. At creation, the fixture called the original Rust future constructor. Both complete 2,360-byte moves, the first poll and the self pointer recovered from the third poll frame establish which future was executing.
Scope and limits
The reporter supplied a formatter example. The runnable store and full test_all regression come from the merged PR. The parent receives that fixture and its workspace registration. A separate public-API control saved and reread a vote, a blank entry and a committed log ID on every build. These results cover the in-process memstore and conformance suite. Deployment, restart durability and Raft cluster behavior were outside the experiment. The origin edge belongs only to the original test_all future. The full comparison stack and its suite-frame view share one debugger stop. Both commits use the same reproduction lock and stable Rust 1.100.0.
