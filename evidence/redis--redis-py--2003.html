Issue findings

Local observation
Redis-py 4.1.2 returned one key from a six-node cluster with 1, 13 and 5 keys on its three primaries. The servers recorded one SCAN on the first primary. Version 4.2.0 contacted all three primaries and returned all nineteen. On the fourteen binary keys published in the follow-up, Redis returned 10 keys and cursor 5 on its first page. The affected client reported cursor zero. The fixed iterator read all fourteen.
What CoroPerf showed
The affected call stack enters _determine_nodes, which selects the default node. A second issue appears even with explicit primary targets. In parse_scan_result the input contains real per-node cursors, but the return statement substitutes zero and scan_iter stops. With COUNT 1 the three primaries supplied 3 keys in their first pages. The intermediate upstream commit preserved the cursor map, then the generic iterator submitted the entire map as a scalar and raised DataError. Continuing separately on each node produced all nineteen keys. The merged fix performs that loop inside the cluster iterator.
Scope and limits
The nineteen-key test preserves the published distribution and the one key the author disclosed. The independent fourteen-key test uses every published key byte. The server chooses its own per-process hash seed, so opaque cursor values and page boundaries can change between runs. Released wheels and the adjacent upstream source revisions were checked against a real Redis 6.2.6 cluster. The client path is a synchronous generator.
