Issue findings

Local observation
One execution of the maintainer raw-asyncpg example uses ten Tasks and one real PostgreSQL connection. Nine prepare calls raise the native InterfaceError that another operation is in progress; one returns data. Gather with return_exceptions=True permits bounded cleanup. The connection closes, PostgreSQL logs shutdown and the process exits 0.
What CoroPerf showed
CoroPerf joins all nine captured exception stacks to their actual Task creation records, recovering the named member-log and moderation submission helpers absent from the native/current exception stacks. An explicitly added API observer records all ten actual Tasks using the same Connection/protocol objects. Together they expose both submission origins and the shared resource; generic Task ancestry alone does not establish connection ownership.
Scope and limits
This is the maintainer standalone driver component on asyncpg0.29.0, not the original Discord bot or SQLAlchemy1.4 beta ORM. Two named submission helpers and bounded exception collection adapt the example for attribution. Those helper names are fixture entries, not recovered Discord registrations. Two earlier authentication failures are preserved; this is the only successful prepared-statement workload. No per-Task connection fix, alternate version or query replay ran. Known upstream guidance to use distinct connections is not a locally tested fix.
