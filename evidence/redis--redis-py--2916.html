Issue findings

Local observation
The reporter’s synchronous program adds one with score 1 and two with score 2, then asks Redis for the zero-based rank and score of two. Redis replied with an integer 1 and a one-byte score, 2. The 4.6.0 client raised TypeError. The 5.0.0 client printed [1, b'2']. Running the same script again reproduced the reporter’s two leading zeros because both members already existed. On an empty set the two ZADD calls each printed 1. The rank outcome was the same in both states. Rank alone returned integer 1, and a scored query for an absent member returned None. Both a released Redis 7.2.0 server and the dated unstable server produced the same replies. The first table shows results shared by the synchronous client and its asyncio companion.
What CoroPerf showed
The synchronous process sent the posted lower-case ZRANK command and read a 15-byte RESP2 array. An independent socket read the same bytes. redis-py 4.6.0 decoded them into [1, b'2'], dispatched the list to int_or_none and called int(response). That scalar conversion raised the reported exception. A normal redis.asyncio.Redis client reproduced the error on the same public command. Its parser, connection and callback all received the same list object. In the 4.6.0 graph, segment 2 records the library creating parse_response at redis/asyncio/client.py line 492. Segment 11 observes the same running coroutine frame at line 551 as it received the callback’s TypeError. The separate stream-reader callback recorded the server bytes while the coroutine was suspended. On the 5.0 development branch, parent e13b239c still dispatched to int_or_none. Change 2a935eb9 removed the ZRANK callback registration, so parse_response returned the decoded list directly. Both source snapshots lacked the withscore keyword on the convenience method. By release 5.0.0 the keyword was available and ZRANK had a registered zset_score_pairs callback. On the reporter’s call this callback returned the original list object. The return path and the independent wire read agree on its two field types.
Scope and limits
The original program used redis.Redis synchronously on macOS with Python 3.9 and an unspecified Redis unstable commit. Replay ran the posted source on Linux with CPython 3.9.15 and the latest unstable commit at the report timestamp. It also ran against Redis 7.2.0. The coroutine certificate belongs to the separate asyncio companion. The synchronous reporter contributes zero coroutine origins, and the shared issue contributes one. Across the eight observed processes, 4 parser coroutines failed on the reported command, 2 failed on the scored wrapper and 22 completed successfully. Release 5.0.0 was already on PyPI when the issue opened on August 25, 2023. The maintainer identified it in a later comment. The two branch commits document an earlier behavioral transition. Separate issue #4428 concerns score bytes versus text under a later client’s protocol and decode_responses settings. This experiment used RESP2 and the default byte decoding.
