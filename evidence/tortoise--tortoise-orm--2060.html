Issue findings

Local observation
Two tasks supplied different defaults for the same missing PostgreSQL row. On the observed parent run, the first task created the row with a. The caller that requested b also received a, and an independent database read found a. No UPDATE ran. With the fix, the second caller received b, one UPDATE ran, and the committed row contained b.
What CoroPerf showed
The original gather call created the task that lost its defaults. Its return sample in update_or_create led through _create_or_get after a conflicting INSERT. That path fetched the existing row and returned it with the creator’s value. The corrected path applies the waiting caller’s defaults. Aligning the two initial reads let the opposite caller win and produced the same role-dependent behavior.
Scope and limits
The missing-row race depends on scheduling. In the default-pool runs the second caller saw the existing row and updated it normally. PostgreSQL readbacks and statement logs establish the committed value and write count. The Python stack identifies the caller and ORM branch.
