Issue findings

Local observation
The bounded shared-connection control confirms that notification iteration holds the driver connection lock while a query waits. A separate historical-caller extension transfers each paused generator after one identical notification, then lets its reader Task be collected. Both later queries have identical native await stacks; the PostgreSQL backends are idle. Generator frames and allocation traces, current Task creation traces and coroutine origins omit the completed readers' application entries.
What CoroPerf showed
A profile event records the running Task at each successful acquisition. The returned generator's actual suspended frame identifies the same connection lock. At the later wait, that lock has no intervening release. Joining its acquisition history to Task creation recovers start_report or start_refresh after the acquirer Task is collected. Two independent batches verify 32 historical callers across both driver versions and both read/query launch orders. Resource-wait edges remain separate from creation edges.
Scope and limits
The experiment uses Psycopg 3.2.3 and 3.3.9 with the pure Python implementation, CPython 3.12.16, PostgreSQL/libpq 14.13 and private local databases. Four bounded controls check the report's shared-versus-separate-connection mechanism; the literal 2022 program is not executed. The historical-reader extension is separate. Explicitly closing the paused generator releases the lock and returns 42; the 32 closed-generator controls complete without waiting. This is application cleanup, not a claimed driver repair. Removing lock history or Task creation prevents attribution. The displayed joins identify historical acquisition samples, not a live owner Task or a query-creation parent.
