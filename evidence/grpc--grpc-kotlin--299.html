Issue findings

Local observation
Two separate coroutine Jobs invoked the same generated unary method on one stub. In the simultaneous-failure trial the server received identical protobuf bytes, and both RPCs returned UNAVAILABLE with the description “io exception”. Both original throwables had callback stacks ending at the gRPC client and omitted the application call. Two batches sent 64 real RPCs.
What CoroPerf showed
The continuation handed to GreeterCoroutineStub.sayHello contained the actual Kotlin Job. Its identity joined the application coroutine’s creation site to the failure at ClientCalls.kt line 295. The independent await checks used JVM reference equality for the throwable. This separated the profile call at MatchedCalls.kt line 11 from the inventory call at line 15, including when both calls carried the same message and the server reversed its reply order.
Scope and limits
The service deliberately emitted the reported status over a real localhost HTTP/2 connection. The report supplied no application or version lock. These traces answer the caller and generated-method questions. Determining the underlying cause of a production network failure requires additional transport or server evidence.
