Issue findings

Local observation
240 bounded, database-free queue-component trials reproduce lost cancellation in SQLAlchemy 2.0.55 and 2.1.6 on CPython 3.11.18. Native cancelling() already exposes the defect. A separate application extension creates two cancelling Tasks through different entries, then collects them before observing the targets. Both targets have matching native stacks, creation traces, coroutine origins and allocation traces; these omit the historical cancelling entries.
What CoroPerf showed
Profile events observe the actual C Task.cancel receiver and a cancelling-counter increment, binding each accepted request to its running actor Task. A weak lifetime registry records actor collection. CoroPerf connects the historical cancel-call sample to that same actor's creation, recovering start_deadline_cancel or start_shutdown_cancel. Two independent batches verify 48 historical issuers across both launch orders: 32 in affected releases and 16 in the fixed release. Cancellation provenance is a separate causal relation, never target creation ancestry.
Scope and limits
The component uses real released AsyncAdaptedQueue through greenlet_spawn, without a DBAPI or database. The historical-issuer extension adds an observation gate and is not the literal upstream program. SQLAlchemy 2.0.56 on Python 3.11 and Python 3.12.16 with both older releases pass the component repair controls; 2.1.7 and Python 3.10 or earlier were not tested. Stock and captured application outcomes agree. Removing cancel history or Task creation prevents attribution. All SQLAlchemy and greenlet Python/native files match official hashed PyPI wheels. The native flags already identify cancellation loss; CoroPerf adds historical issuer identity, not root-cause discovery or a new repair. No production overhead result is claimed.
