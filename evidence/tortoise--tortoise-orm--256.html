Issue findings

Local observation
The reporter inserted 0, 27.27 and 9.99 and ordered the resulting objects by their decimal field. Both affected builds returned the values in that insertion order. The fix and release 0.15.5 returned 0, 9.99 and 27.27.
What CoroPerf showed
The planner passed the bare column to ORDER BY. SQLite had stored the values as text, and its execution trace confirmed the comparison used that column. In an independent check, changing only the ORDER BY expression to CAST the column AS NUMERIC recovered every expected bill and tip position. The fix generated that cast. The local relation-prefetch example links the task that returned the misordered bills to BaseExecutor._execute_prefetch_queries. The tip query used a separate prefetch task.
Scope and limits
The original report supplied model and query fragments. The local wrapper supplied initialization and invoked the reported operations. Release 0.15.4 is the release immediately before the confirmed fix release. The coroutine-origin evidence comes from an additional reverse-relation query on 244 restaurant checks, grouped by service day. All reference rankings used exact decimal values from the CSV and row ID to break ties.
