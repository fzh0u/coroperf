Issue findings

Local observation
The reporter’s asynchronous Python program submitted six translation prompts to CTranslate2. With GPT-2 on CPU, the longest input had 204 tokens and the shortest had 56. The requested maximum was 80 new tokens. The 3.15.1 worker called the decoder 80 times and returned an empty sequence for the longest input. The 3.16.0 worker called it 191 times and returned 43 tokens for that input. The same output list passed from the executor thread through the generate coroutine to run_test.
What CoroPerf showed
The maintainer’s deterministic regression isolates the length calculation. After processing the common prompt length, the longer row still had two supplied tokens to consume. In both greedy and beam search, the affected decoder ran at positions 2 and 3, consumed those tokens, and returned an empty continuation from native search. The first fixed wheel also ran at positions 4 and 5 and returned [2497, 262] (“ saw the”), matching independent PyTorch inference. Reversing input order moved the empty result with the longer prompt. The archived native stacks place the positional decoder inside search. CPython recorded run_test creating the generate coroutine at line 99 and observed the same frame resume with the affected result at line 69.
Scope and limits
The original deployment used a 13B Vicuna-family model, CUDA, and int8/float16. This replay used GPT-2, its tokenizer and float32 on CPU. It retained the posted run_test and generate definitions, prompt text and generation arguments, selected six inputs with a recorded seed, and stopped after one batch. The first table gives the sampled run’s actual lengths. The pytest table uses deterministic generation. Only the Python generate coroutine contributes an origin. The executor and native worker have their own recorded thread identities.
