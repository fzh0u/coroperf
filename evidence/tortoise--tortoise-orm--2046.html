Issue findings

Local observation
The abstract base model requests newest-first order. Its Book subclass specifies the table name. On the three posted books, Tortoise ORM 1.1.8 and the immediate fix parent returned IDs 1, 2, 3. first() selected the oldest book, ID 1. The fixing commit and 1.1.9 returned IDs 3, 2, 1 and selected ID 3. Sorting the original timestamps in Python and reading the saved SQLite files with explicit descending order both put ID 3 first.
What CoroPerf showed
The metaclass samples show the base model’s descending ordering and the child’s empty ordering in the affected build. The query resolver used that same child metadata object, and SQLite received a SELECT without ORDER BY. The fix copies the base ordering when the child omits it. With the repaired metadata, the resolver emitted ORDER BY on created_at descending. Explicit ordering worked on every build. On the affected wheel, segment 4 records the unstarted QuerySet._execute coroutine created by QuerySet.__await__ at queryset.py line 1294. Segment 6 includes its pinned frame while the SQLite client returns the three IDs. At segment 7 that same instance returns the list received by the public caller. Segments 1–3 sample the earlier synchronous decision that determined the order.
Scope and limits
The issue supplied the model definitions and three rows without identifying a database engine or release. This replay uses SQLite, preserves the timestamp strings and awaits the two posted query alternatives separately. The sequence of an unordered SQL query depends on the database and plan. The coroutine match covers query execution on the event-loop thread.
