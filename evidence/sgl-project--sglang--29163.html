Issue findings

Local observation
Four concurrent Kimi-K2.5 prompts of 6,000 to 7,500 tokens share one executor WorkItem. The stock dynamic batcher uses the Python tokenizer path for each input. The proposed change uses direct encode for these inputs. Median wall time for the four-request batch falls from 141 to 43 ms across ten timed pairs after warmup, with the same token IDs. A second run gives 138 and 43 ms.
What CoroPerf showed
The four _encode_plus worker stacks are identical. The current prompt is the same object as an input in the active WorkItem. The batch pairs that input with the exact result Future seen when the request entered the queue. This identifies the waiting Task and its launch stack. The selected observations 8 and 9 go back to batch submission records 4 and 5, then to separate request creations 0 and 1.
Scope and limits
This CPU component run measures the batcher and real tokenizer, without model inference. The checked main revision contains the same batcher as the proposal base. The issue and PR closed for inactivity. For default calls the proposal preserves the token IDs used by TokenizerManager and omits the stock attention_mask key. Explicit truncation and attention-mask requests produced equal results in the tested comparison.
