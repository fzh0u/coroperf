Issue findings

Local observation
The pinned Dynamo Python frontend repeatedly copies the token-ID prefix while the vLLM DeepSeek-R1 parser scans it for a reasoning delimiter. At 8,192 single-token reasoning chunks, two run orders give median frontend thread CPU times of 328–330 ms for the base and 120–121 ms for PR #18728. At 16,384 chunks, the medians are 1,097–1,100 ms and 243–245 ms. The per-chunk envelopes, final content, and token usage match in every arm after removing the wall-clock created field. The proposed token-prefix implementation passes all eight selected upstream tests.
What CoroPerf showed
The two parser samples have identical execution frames on one event-loop thread. The actual Task and async-generator frame identify each request's postprocessor, joining record 4 to 2 and 5 to 3 at the common dispatch site. The same scheduled asyncio Handle and request object reach records 0 and 1, the interactive and batch submissions. Stock asyncio debug Task creation traceback reaches dispatch and omits the two application launchers. The joins follow the right request in both launch orders on both revisions. The interactive request performs 66 parser calls and the batch request performs 258.
Scope and limits
The component replay runs Dynamo's original _generate_and_stream and StreamingPostProcessor with vLLM 0.33.0's DeepSeek-R1 parser. It supplies prepared token chunks in process and substitutes the detokenizer interface. The benchmark measures thread CPU for stream consumption on CPython 3.12.4, with a warm-up and five measured trials per arm per order. Model inference, transport, and other parser families were outside the comparison. The issue and candidate PR are open.
