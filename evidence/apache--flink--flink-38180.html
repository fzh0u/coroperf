Issue findings

Local observation
One successful bounded run of the released Flink 2.1.0 Task component throws OriginalFailure in each of two invocations. The controlled cleanup calls failExternally with CancelTaskException. Both Tasks finish FAILED with no recorded failure cause. Their physical exception stacks are identical and omit the two historical Task construction entries.
What CoroPerf showed
Standard JDI records the actual Task receiver at constructor exit and finds that same receiver in the exception stack. CoroPerf joins each observed failure to its own Task construction, recovering importBranch or refreshBranch. Separate endpoint checks read actual Task references and verify both mappings after graph construction. Native JFR in this same execution records both original exceptions and both worker-thread starts; these recorded stacks omit the historical construction entries.
Scope and limits
This is a Task-only application extension using real released SDK classes, official test builders and a bounded shuffle environment. It does not reproduce a production cluster or the literal upstream application. Native JFR already preserves the original exception; CoroPerf adds historical creator attribution. Earlier failed fixture assertions are retained separately. The final successful workload was executed once, with no version, order or repetition matrix. Fixed-release behavior, production overhead and scheduler-level ancestry were not measured.
