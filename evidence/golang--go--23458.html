Issue findings

Local observation
The reporter’s unchanged HTTP server started one labeled goroutine. Go 1.9.2 and 1.14.7 produced a binary profile sample for the worker with zero labels. Go 1.15 and 1.23.0 put a-label=a-value on that worker’s sample. Each release ran the original program, a two-worker control, and a control that exchanged the two label arguments. Two batches launched 24 separate server processes.
What CoroPerf showed
The binary profile describes the aggregation problem. In the old pair runs, two workers in main.waitForWork collapsed into one sample with a count of two. The runtime dump kept separate goroutine IDs and creation sites at main.startImport and main.startRefresh. The released Go 1.15 profile contained two labeled worker samples and the profile writer stack included the label-aware runtime entry point. Two timed Go 1.9.2 runs link GoCreate at main.main to GoStop at main.Func by goroutine ID. Their creation-to-park intervals are 200.422 µs and 91.712 µs.
Scope and limits
The timed intervals use the Go runtime trace clock from creation to the first park at select {}. The text dump supplies a retrospective check of goroutine ID and creation site. Binary pprof records aggregate stacks and labels. Each control worker separately read its runtime label and printed its ID. Swapping labels preserved each worker’s creator and changed the label it reported. This experiment measured goroutine profiles on Linux amd64.
