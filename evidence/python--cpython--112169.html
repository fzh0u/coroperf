Issue findings

Local observation
In a gated two-worker experiment, the numeric lookup is submitted to the single-thread default pool. It stays pending when the private-pool worker is released and dispatches only after the default-pool worker exits its blocking work. The median construction-to-dispatch delay is about 125 ms with the shared pool and 0.18 ms when the blocking work moves to a dedicated pool. The two worker stacks and asyncio Task diagnostics omit the original callers.
What CoroPerf showed
The snapshot of the default-pool worker matches the WorkItem created at run_in_executor. That work holds the same request object that the shared broker dequeued from the application queue, so its enqueue stack identifies launch_profile in the displayed run (4 → 10 → 15). The second chain (5 → 11 → 16) identifies the concurrently busy private-pool worker. Swapping pool assignments swaps the caller responsible for the delay.
Scope and limits
The two stacks are from a Linux replay on CPython 3.11.15, with additional controls on 3.14.3. The resolver uses a numeric loopback address and the workload sets the occupation interval. The measurements characterize executor queueing in this replay. Calls to an external DNS server are outside its scope.
