Issue findings

Local observation
The reporter inserted a and b into the left table and c into the right. SELECT DISTINCT on the left followed by UNION ALL returned a, b and c on all six builds. An outer COUNT(1) returned 2 on SQLite 3.42.0, 3.43.0 and the fix parent. The fixing commit restored the count to 3. Disabling the unused-column optimization on the parent also restored it to 3.
What CoroPerf showed
In the parent trace, the planner treated the projected values as unused because the outer query counted a constant. It replaced both branches’ column reads with NULL, even though the left branch needed its values for DISTINCT. The duplicate check accepted the first NULL and discarded the second. Only one left row and the right row reached the counter. The fix checked each branch for DISTINCT and preserved the column reads. The debugger then saw two distinct keys, a and b, and three calls to the counter.
Scope and limits
The native trace follows one prepared COUNT(1) statement through compilation and execution on a single thread. It establishes no application coroutine origin. Both adjacent development builds identify themselves as SQLite 3.44.0, so the table labels them by Fossil check-in. The independent PostgreSQL 14.13 replay added the derived-table alias that version requires.
