Issue findings

Local observation
Two synthetic sessions alternate on one Ollama runner slot. On four repeat turns, the default runner evaluates 494 to 512 prompt tokens per turn. Forwarding a zero slot similarity threshold leaves four prompt tokens to evaluate on each repeat. Median prefill falls from 1.86 s to 52.3 ms. All six completion texts and generated token counts agree between arms. Reversing the session order also gives four evaluated tokens on each repeat with the local patch.
What CoroPerf showed
Both final timing callbacks have identical execution frames on the same persistent Go worker. Go's traceback with ancestor capture shows the worker's launch and omits both request launchers. The exact work pointer received by the runner worker and returned to the submitter connects each callback to its channel send. The submit goroutine's creation record then identifies launchCatalog or launchResearch. The catalog path is 8 to 7 to 6 and the research path is 11 to 10 to 9. Native runner logs show the default similarity-based slot selection and the cached prompt restoration with the opt-in override.
Scope and limits
This component test uses the Ollama v0.40.16 Go launcher and streaming completion reader, llama.cpp b12177, and Qwen3.5-0.8B Q4_0 on a four-thread CPU. The two session launchers and their shared worker are fixture code. The report's Qwen3.8-27B GPU and eight-slot checkpoint behavior remain untested. The Ollama issue is open and the configuration patch was tested locally.
