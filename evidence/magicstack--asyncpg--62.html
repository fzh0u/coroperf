Issue findings

Local observation
PostgreSQL stored the inclusive range [-infinity,infinity]. Reading it with asyncpg 0.8.3 raised ValueError: ordinal must be >= 1. A finite date exposed the same bug silently. PostgreSQL returned 1999-12-31, and the old driver delivered 0001-01-01. The 0.8.4 wheel and its exact source commit read the infinite endpoints as Python’s minimum and maximum dates and returned the finite date correctly. The reporter’s minimal script produced the same outcome in both trials of each build. The first table also shows the reverse direction, binding Python date.min and reading PostgreSQL’s text for that value. In 24 comparisons the received binary fields agreed byte for byte with independent libpq and PostgreSQL COPY reads.
What CoroPerf showed
PostgreSQL encodes a date as a signed count of days from 2000-01-01. Its bytes for 1999-12-31 are ffffffff (−1). Its negative-infinity sentinel is 80000000 (−2147483648). The loaded 0.8.3 decoder compared against −1. When the actual infinity arrived, the decoder added −2147483648 to the epoch ordinal 730120 and passed −2146753528 to date.fromordinal. GDB recorded that argument and the decoder’s failed return. The fix uses the signed 32-bit minimum for DATE. On the finite −1 input the corrected decoder passed 730119 to date.fromordinal and returned December 31. Inside Connection.fetch, asyncpg/connection.py line 268 created _get_statement. CPython sampled that same coroutine object and frame at line 233 as it returned the prepared statement (0.8.3 graph segments 3 and 21). GDB found the same statement and waiting Future on the active protocol while the receive callback decoded the row. The reporter had created the outer fetch at reporter.py line 12. That fetch resumed with the ValueError (segments 1 and 29). On 0.8.4 it returned the inclusive range (segments 1 and 31). In a separate finite-only test, PostgreSQL evaluated its range-containment operator for four windows and nine probe dates. Python evaluated lower ≤ day < upper using the returned endpoints. Moving a lower bound from 1999-12-31 to year 1 admitted five extra dates, including 1900-01-01. Moving an upper bound to year 1 excluded two valid dates. Each affected build disagreed on seven of 36 checks in each trial. Both corrected builds agreed on all 36.
Scope and limits
The opening report queried the author’s application table and described 0.7.0 as working. This replay uses the author’s later self-contained test_62 script, CPython 3.6.5 and a local PostgreSQL 10.23 server. The four builds represent two commits, each tested as a released wheel and a source build. Explicit infinite DATE endpoints are inclusive values here. The separate unbounded-range control returned absent endpoints on every build. Cases with finite December 30, the epoch date and positive infinity also agreed. For timestamp one microsecond before the epoch, 0.8.4 still returned 2000-01-01 00:00:00.999999, one second late. That fractional-timestamp behavior belongs to separate issue #363. The coroutine-origin count for #62 is one. GDB stops describe ordinary native callback frames.
