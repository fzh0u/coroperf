Issue findings

Local observation
The table already contained (1, 1, 1). The batch proposed (1, 2, 1) and (3, 2, 2). The first candidate reused primary key 1. The second could use secondary key 2 because the first candidate never entered the table. Both affected releases reported INSERT 0. Every gateway in each three-node cluster returned only the seed row, including reads forced through the primary and secondary indexes. The January alpha and v19.1.0 reported INSERT 1 and stored (3, 2, 2). Splitting the batch or reversing the two candidates recovered the valid row on the affected releases.
What CoroPerf showed
The sampled SQL connection goroutine reached strictTableUpserter.getConflictingRows. On the December alpha it reserved the first candidate’s secondary key while preparing the storage reads. Its next lookup found the same key in the same Go map and marked the second candidate for omission. Both releases then read the same four keys from storage. Only the first primary key existed. The January alpha checked storage first, omitted the first row and reached row.Inserter.InsertRow with the values (3, 2, 2). The creation stack and scheduler observation match the goroutine performing these decisions.
Scope and limits
The report gives the SQL and expected PostgreSQL result. Its CockroachDB version is unspecified. Native stacks come from the two dated alpha releases on opposite sides of the fix. The table below the original result covers 24 extra candidate orders. Each family has six orders and the counts include any statement error. The six errors on v19.1.0 occurred when proposed rows conflicted with each other. Its default plan used two index lookups and an inserter. Switching the same release to its strict upserter handled all six orders. Both plans passed the original reported SQL.
