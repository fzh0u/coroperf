Issue findings

Local observation
The original image pipeline generates 10–19 patches per image. On Ray 2.53.0, take(1) returned one 128-component vector. On Ray 2.54.0, it returned 18 vectors. In a separate observed run on 2.53.0, workers extracted and encoded 16 patches for UUID_0. Only 1 reached the grouping function. The table follows the same image through each worker stage within the observed run. The stock run uses the original unseeded random generator independently.
What CoroPerf showed
GroupedData.map_groups marked the grouping function as preserving row count. The stack in LimitPushdownRule._push_limit_down records that flag on the batch operator and the rule moves Limit ahead of grouping. One input patch then becomes one incomplete output image. The fix keeps Limit after grouping. On five known values, reversing only the flag recovered their full sum of 115 on the affected release and reproduced the partial group on the fixed release. Even the row-preserving centering function returned a different feature value when its worker saw one input.
Scope and limits
The measurements use the reporter’s Ray 2.53.0 release and the first fixed release, 2.54.0, with Linux CPU workers. Full and limited reads of the posted script can select different images or regenerate features. A separate six-image workload verifies every returned pixel and feature component against a scalar calculation for 54 patches. The captured optimizer calls are synchronous.
