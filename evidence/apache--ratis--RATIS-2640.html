Issue findings

Local observation
A healthy group of three voters (s0, s1, s2) had a fourth server ready to join as listener l0. The Java client supplied all four IDs to AdminApi.setConfiguration. With the array overload, 3.2.2, 3.3.0 and the immediate parent threw NullPointerException. The servers counted zero configuration RPCs and the three voters retained their original configuration. The list overload succeeded on all five builds. The fixed array overload also sent one RPC, committed the joint and final configurations, and let l0 apply the subsequent write. Each table entry was checked on two fresh groups.
What CoroPerf showed
In a separate four-server run, a debugger followed the production client reasserting its installed membership. On 3.2.2 the builder wrote a list backed by the voter array into the listener field, then overwrote it with a list backed by the listener array. The voter field was null when Preconditions.assertUnique threw. The debugger saw exception object 4491 both at the throw and in the caller’s catch. On 3.3.1 the builder wrote each array to its own field. AdminImpl constructed request object 4702, the gRPC serializer received that same object, and the successful reply matched call ID 17.
Scope and limits
The reporter supplied the API code and exception stack. The fix supplied the two JUnit tests and peer IDs. Those tests capture configuration arguments at the client API boundary. The live listener additions also checked server RPC counters, group membership and replicated log entries through writes before and after the call. Ratis 3.2.2 omits an optional configuration field in GroupInfo replies. Its member IDs, division configuration and committed log entries establish the result. The cross-version control below changes one voter’s priority on a single-voter leader. The graphs follow synchronous work on the Java main thread and contain zero creation edges.
