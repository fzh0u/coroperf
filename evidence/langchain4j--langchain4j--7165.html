Issue findings

Local observation
With the registered callback held, the exact pre-fix StreamingTest rethrows the expected stream error and then fails the list-size assertion. The merged test waits in its latch helper and passes when the callback completes. In a two-caller replay, both captures rethrow the exact original exception while both callback lists remain empty. Checking immediately fails both assertions, and waiting for the callback notification passes both. The two orders produce the same result.
What CoroPerf showed
Both later user callbacks have identical physical stacks through AiServiceStreamingResponseHandler.onError. The real response handler passed into the threaded mock and the exact Throwable object identify each callback. This joins batch observation 2 to creation 1 and interactive observation 3 to creation 0, even though the later launch records its callback first. Each creation stack reaches the caller's capture and TokenStream.start. Reversing the launches and callback releases preserves the matches. The joins show that capture's terminal observation and the application's callback side effect occur at different points in the same stream.
Scope and limits
The JDK 25 replay uses the published LangChain4j 1.24.0 runtime and langchain4j-test 1.24.0-beta34, the pinned pre-merge and merged StreamingTest files, and MockStreamingChatModel with no provider. The release and merge parent have identical relevant onError code, capture helper, and mock. The deterministic control holds only delivery to the user error callback. All ten ordinary merged StreamingTest cases also pass. GitHub still lists issue #7165 as open. The maintained test correction in PR #7217 is merged.
