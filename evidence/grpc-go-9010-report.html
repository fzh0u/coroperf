Which completed gRPC method created the child goroutine still waiting?

中文案例

One Go1.23.0/grpc1.60.1 bufconn Health/Check RPC returns SERVING. Its controlled child goroutine171 remains in channel receive during a bounded 30ms snapshot. The native child dump records only enqueueContinuation as immediate creator; the earlier server-handler goroutine170 is absent. Normal child and server cleanup completes with process exit0.

Standard runtime trace records goroutine171 birth with the full creator stack through service.Check, the generated gRPC handler and Server.processUnaryRPC. Child self-reported native ID and independent all-goroutine snapshot match the same runtime trace ID. CoroPerf joins birth to the waiting stack and restores the historical gRPC method origin absent from the current stack. The measured trace waiting interval is about 30.96ms. The source information already exists in standard Go trace; CoroPerf supplies the normalized identity join and combined view.

This is a controlled diagnostic component illustrating issue9010 on cached Go1.23/grpc1.60.1, not a current Go1.27 regression, the original goroutine-label implementation or a panic/crash reproduction. One in-memory RPC and one child continuation ran. It does not establish a stuck server, resource leak, cross-process request ID or complete RPC causal graph. No modern-label, fixed-version or additional RPC comparison ran.

Go1.23.0/grpc1.60.1 的一次真实 bufconn Health/Check RPC 返回 SERVING；受控子 goroutine171 在 30 毫秒有界快照中等待 channel。原生子栈仅记直接创建函数 enqueueContinuation，更早的服务端 handler goroutine170 已不在快照中。正常清理子任务与服务端，进程退出 0。
