Issue findings

Local observation
A fresh process reopened the node’s Bolt database and restored ten application records from a snapshot at index 11, term 1. With no new application write, the original revision accepted a manual snapshot and created a second file at index 0, term 0. Both state files contain the same 384 bytes. The fixed revision returned “Nothing new to snapshot” and retained the original file. Two restarted followers in the same three-voter cluster showed the same difference while the leader stayed up.
What CoroPerf showed
NewRaft restores the index and term on the Raft object before it starts the state-machine goroutine. The Go trace records that goroutine’s creation in NewRaft and its first snapshot request in runFSM. In the recorded single-node restart, the applied index had reached 12, but runFSM on goroutine 9 still held local index 0 and term 0. Goroutine 10 in takeSnapshot read those values from the same request and passed them to the snapshot store. After a Barrier reached runFSM, the local index advanced and both revisions produced valid snapshots.
Scope and limits
The experiment covers the 2015 revision immediately before PR #58 and its fix. The local TCP cluster used Bolt storage and kept all snapshot files. All ten application records survived the restart. Stock source establishes the file behavior. Go runtime traces and local values come from separate builds with logging at the relevant source lines.
