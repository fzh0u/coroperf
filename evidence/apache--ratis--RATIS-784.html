Issue findings

Local observation
A writer appended three receipts to a fresh local Raft log and waited for each append to finish before reading the registered syncBatchSize gauge. The parent of the fix returned 0 after each write, even as the completed sync counter advanced to 1, 2 and 3. The source fix and the 0.5.0 Maven release returned 1 each time. On every build the segment received three data syncs plus one earlier sync for the file header. The 48-, 49- and 50-byte record frames and the 8-byte header accounted for all 155 bytes. A second JVM reopened the log and recovered the three original receipts.
What CoroPerf showed
On the parent, the Java Debug Interface (JDI) captured the worker completing the data force (segment 8) and clearing pendingFlushNum (10). The registered gauge then read that field on the same worker (14) and returned 0. On the fix, flushWrites saved the difference between the last written and previously flushed log indices in flushBatchSize (7). The gauge read that saved count after the pending count had been cleared (15). In the separate six-record workload, segment write bytes and the following successful syncs identify each physical batch. With the default threshold the batches contained 3, 2 and 1 entries. Setting forceSyncNum to 1 gave six single-entry syncs for the same submissions. Both corrected builds reported the size of the last actual sync at each of the three sampling points.
Scope and limits
The JIRA ticket supplied a description and patch. The local harness follows the existing upstream testAppendEntry pattern and adds metric reads. The measurements cover the file-backed SegmentedRaftLog, registered metrics, data syncs and readback after an orderly close. Replication and quorum commit are outside this workload. The grouped experiment uses state-machine write futures to control when a submitted group can complete. A second JVM recovered all six entries and their side data. JDI sampled the worker and gauge caller threads. The captures contain no verified coroutine origin.
