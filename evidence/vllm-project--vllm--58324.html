Issue findings

Local observation
In one scheduler pass, the 64-chunk session copies 63 already covered audio features and the 4-chunk session copies three. The request-owned prefix patch reduces this to one copy for each session. Both sessions produce the same 64 and four output deltas in both test orders. With an initial history of 1,024 features, median CPU time for one NewRequestData.from_request call is 1.36–1.38 ms on main and 6.66–6.82 µs with the patch, measured with collection off.
What CoroPerf showed
Records 4 and 5 have identical execution stacks in the same Scheduler.schedule call. The NewRequestData.from_request frame holds the exact persistent Request captured when the scheduler first accepted it. The submitting live asyncio.Task matches the coroutine created by RealtimeConnection.start_generation. This joins 4 → 3 → 1 to captioning and 5 → 2 → 0 to live notes. Swapping which launcher runs the long session swaps the associated copy counts.
Scope and limits
This CPU fixture runs the real vLLM generation Task, streaming scheduler, and request conversion with in-process delivery, synthetic features, and supplied model output. Timing covers conversion only. The worker still receives a full feature list per step. Issue #58324 and PR #58334 are open. The PR applied to main 31814a6f6f2d raises AttributeError on the slotted feature class. The tested local adaptation stores the covered prefix on the resumable Request.
