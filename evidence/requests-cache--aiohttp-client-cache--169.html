Issue findings

Local observation
A single client requested the same 42-byte document three times. All three responses had HTTP status 200 and declared a 42-byte body. The server received one GET. On 0.8.2 and the immediate fix parent, the third stream read returned zero bytes while the cached response still held all 42. On the fix and 0.9.0, every stream read returned the full document. Plain aiohttp and standard-library clients each made three origin requests and returned all 42 bytes every time.
What CoroPerf showed
On 0.8.2, DictCache.read (segment 22) returned the same cached response. Its content getter (24) returned the exhausted reader. The third read started at cursor 42 with zero bytes buffered (26). CPython recorded the application creating StreamReader.read (25). The same coroutine frame was running when _read_nowait returned empty bytes (30). On 0.9.0, DictCache.read called CachedResponse.reset, which cleared the reader on the same response (25). The content getter called CachedStreamReader.__init__ (33) and returned the new reader (34). The third read started at cursor 0 with 42 bytes buffered (36) and returned all 42 (47).
Scope and limits
The observer followed sequential GETs through the in-memory backend on the two release wheels. The loopback fixture replaces the reporter’s public URL and corrects a repeated variable name in the interactive transcript. Both adjacent source builds identify themselves as 0.8.3, so the table labels them by commit. The landed regression uses response.read() and passed on all four builds. Switching the two cached reads to response.content.read() reproduced the reported difference. The CSV table uses a separate 15-byte document and measures what the next cache hit could parse.
