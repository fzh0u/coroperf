Issue findings

Local observation
The CPU replay completes the actual PyZMQ object Future awaited by the historical receiver. Two real tokenizer calls then occupy its event-loop thread before the receiver can resume. In five trials per mode the median ready-to-resume time is 32.6 ms on the loop and 0.050 ms with the same encoding work on worker threads. All eight first-token responses and both encoded outputs agree.
What CoroPerf showed
The actual receiver Task connects handle_loop record 5 to launch record 0. Matching each active preprocessing Task and input object joins identical encode stacks 3 and 4 to prompt and caption launch records 1 and 2. Their observed CPU intervals fall between Future completion and receiver resumption. Reversing launch order and swapping input sizes moves the work to its corresponding caller.
Scope and limits
The fixture uses pinned SGLang receiver code, loopback IPC, and two controlled CPU preprocessing calls with a pinned BERT tokenizer. In an isolated receive-loop comparison, PR #17069 dispatches chunks of 3, 3, and 2 but still sees about 32 ms before resuming. The issue closed for inactivity and the PR closed before merge. The reported model and production latency remain outside this replay.
