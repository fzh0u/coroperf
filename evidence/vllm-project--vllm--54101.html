Issue findings

Local observation
With eight requests, a 100 ms loopback service delay, 50 scheduled requests per second, and a concurrency cap of one, the affected client reports mean E2EL of 101.9 ms. The merged client reports 101.9 ms for the same endpoint metric, 287.4 ms of mean client queueing, and 389.3 ms of queue-inclusive E2EL. All replies are identical in content.
What CoroPerf showed
Seven of eight Tasks encounter the held semaphore. Requests 2 and 7 have the same wait and send stacks. The live Task and actual RequestFuncInput join wait 5 and backend entry 17 to creation 4, and wait 16 and backend entry 22 to creation 15. In the traced trial these requests spend 166 and 581 ms respectively between semaphore entry and the backend's start timestamp.
Scope and limits
This comparison runs both pinned benchmark functions and real HTTP clients against a deterministic loopback server. The merged queue clock starts at benchmark Task submission. It measures the wait before the backend timer, with a separate queue-inclusive E2EL for finite-rate runs. The pooling path passes the same accounting check. No inference server runs in the fixture.
