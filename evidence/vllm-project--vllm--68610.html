Issue findings

Local observation
With one active slot and one previously examined request waiting, two more requests enter before the pending model result completes. The base reports 3 capacity waiters. PR #68700 reports 1 for that step and 3 after the next scheduling pass when all three are still waiting. The raw counts remain 1 running and 3 queued in both versions. Reversing the two launches gives the same counts.
What CoroPerf showed
Both requests enter Scheduler.add_request through identical engine stacks, after their frontend Tasks have completed. The complete ADD message matches the actual vLLM client send to its local receive, and the scheduler sees the exact decoded Request inserted in the input queue. The interactive observation follows 4 → 2 → 0. The batch observation follows 5 → 3 → 1. This recovers who submitted each request that arrived after schedule() and reached the queue before statistics were recorded.
Scope and limits
The CPU fixture executes vLLM's asynchronous client send, request preprocessing, engine input handling, and scheduler. It uses in-process ZeroMQ and supplies a deterministic model result. Tensor parallel execution, HTTP metrics scraping, and the gateway in the report are outside the comparison. The issue and PR are open.
