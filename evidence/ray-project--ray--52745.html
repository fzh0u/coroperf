Issue findings

Local observation
On Ray 2.45.0, 32 concurrent HTTP streams each send 64 ordered events. Forwarding each event separately transfers 2,048 Ray results and delivers 3,250–3,476 events/s across two benchmark orders. Flushing the first event immediately and grouping the rest by eight lowers the count to 288 and delivers 8,787–8,802 events/s. The co-located generator bypasses the deployment hop and delivers about 9,200 events/s. All three arms return exactly the same event contents and order.
What CoroPerf showed
At the Ray result wrapper both physical stacks are identical. The live DeploymentResponseGenerator, actual ActorReplicaResult and owning Python async-generator frame connect each read to the creation of its HTTP response body. Record 1 joins to launch_lookup through record 0, and record 3 joins to launch_summary through record 2. The same two stacks belong to the opposite routes when the clients start in reverse order.
Scope and limits
The benchmark uses a local HTTP ingress and two actual Serve replicas with synthetic SSE output, five runs per arm in each of two benchmark orders. Throughput counts events at the client, and grouping changes arrival cadence. The co-located path isolates the extra deployment hop in Ray 2.45.0. The reporter closed the issue after HAProxy and direct streaming became available. The tested workaround is application-side grouping.
