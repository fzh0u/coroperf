Issue findings

Local observation
With skip_tokenizer_init enabled and two tokenizer workers requested, the parent revision reduces the worker count to one. Both replies pass through the same live receiver Task. Merged PR #30682 preserves two workers. Two actual TokenizerManager receiver Tasks deliver the replies through separate Unix IPC endpoints. Both revisions return the original token IDs for both requests, and both use one configured detokenizer.
What CoroPerf showed
Both receiver observations have the same SGLang execution stack. Matching the live Task, coroutine, and manager joins interactive record 6 to receiver creation 0 and batch record 4 to creation 1. Each manager sets the exact Event awaited by its request. The request observations independently join interactive 7 to creation 2 and batch 5 to creation 3. The scheduler packet lists the batch response first, while the request IDs and endpoint mapping still recover both correct owners.
Scope and limits
The CPU fixture runs pinned SGLang configuration, scheduler send, router, and receiver methods. It constructs the scheduler output and creates receiver and request Tasks in the harness. The result establishes the worker-count and reply-routing change. Full server startup, Rust frontend integration, and production throughput remain outside this replay.
