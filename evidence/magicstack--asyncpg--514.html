Issue findings

Local observation
The reporter stored 0.00003000 in a NUMERIC(1000,8) column. The original script returned 0.000030000000 on asyncpg 0.18.3 and 0.20.0, and 0.00003000 on 0.20.1. PostgreSQL sent the same numerical value and a display scale of eight. On each release we also ran one read-only query three times on the same connection. Selecting the text decoder removed the four extra places on both affected releases. Restoring the default binary decoder brought them back. The last two columns count scale mismatches across 22 stored rows in each column type.
What CoroPerf showed
The affected fetchrow coroutine returned the same Record and Decimal later read by the caller. Its creation and return stacks identify where that query originated. PostgreSQL encoded the number as one base-10,000 group containing 3000 at weight −2. The old decoder’s fractional-digit calculation omitted the leading zero group and added four trailing zeros. In the fixed decoder the native stack recorded eight fractional digits and zero adjustment. This explains why the numerical value stayed equal while the Decimal exponent changed. Copying the actual result into an unconstrained NUMERIC column three times persisted the extra places at each step.
Scope and limits
The stock release runs used Linux, CPython 3.7.6, asyncio and PostgreSQL 11.5. The creation stack comes from a separate observed run of the reported SELECT. It follows one physical fetchrow coroutine. Protocol decoding ran in an event-loop callback. Native decoder locals were measured on a debug build of the fixed release. The affected release’s arithmetic is inferred from its shipped source, the wire values and the same-connection codec switch.
