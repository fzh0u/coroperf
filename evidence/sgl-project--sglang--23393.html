Issue findings

Local observation
With the Kimi-K2-Thinking tokenizer and Transformers 5.3.0, three incremental detokenizer packets of 1,024 rows use 4.27–4.37 s of thread CPU time with the old default and 51.7–52.2 ms with PR #23409's cached default. For 128 rows, the medians are 530–547 ms and 6.43–6.48 ms. Every text fragment and output token ID matches. Enabling the cache on the base and disabling it on the merged revision reproduce the corresponding timing regimes. With special-token filtering off, the 128-row control stays around 5 ms on both defaults.
What CoroPerf showed
Two identical decode stacks in one worker belong to different rows of the same scheduler packet. Matching each live token list to its row and using that row's request ID joins execution records 2 and 3 to frontend Task creations 0 and 1. Both Tasks receive the expected result via the actual ZeroMQ IPC and TokenizerManager response path. Reversing the launches and packet rows preserves the matches. The old path computes all_special_ids 20 times for each traced row. The warmed cache avoids all 20 original property evaluations on each row.
Scope and limits
The CPU replay uses the pinned detokenizer and the official Kimi tokenizer with prepared incremental token IDs. Five measured trials follow one warm-up per default and order. Each trial measures all three detokenizer packets, including incremental assembly. The identity evidence traces a separate two-row local IPC replay and the genuine frontend response coroutine. These measurements cover the detokenizer component. The upstream issue reports client inter-token latency on a larger GPU deployment. The issue is closed and the default change is merged.
