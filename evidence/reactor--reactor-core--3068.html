Issue findings

Local observation
One bounded check of Reactor 3.8.8 confirms that forceful bounded-elastic dispose interrupts a running SchedulerTask. The native InterruptedException stack identifies the blocking operation but omits the earlier submitOrderSynchronization entry.
What CoroPerf showed
Standard JDI observes the actual SchedulerTask constructor receiver and the receiver on the interrupted worker stack. Both have object ID 431. A separate read of the application returnedTask field confirms the same object. CoroPerf joins the saved creation and interruption events and recovers the historical submission entry.
Scope and limits
This is a one-task component adaptation: Thread.sleep replaces the reported blocking HTTP wait. Forceful interruption agrees with dispose semantics; the case demonstrates creator attribution, not an incorrect API contract. Only one workload ran. The collector exits 1 during child shutdown after saving the evidence, so native process exit status is unverified. Capture ends at interruption; the missing terminal event does not imply a live or leaked task. No graceful variant, fix, alternate version, production traffic or overhead measurement ran.
