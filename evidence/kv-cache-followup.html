LMCache #1034：补齐 pin 传递证据

受影响 base 的 LMCacheLookupServer.process_request 明确调用 engine.lookup(token_ids, pin=True)。适配器在 need_to_allocate <= 0 时提前返回，尚未登记 load_specs；retrieve 中存在 unpin。这补齐了上一轮缺失的传递环节，仍不代表已运行验证所有调度路径。

该 pin 是缓存淘汰保护状态，不是 CUDA host memory pinning。CoroPerf 需要把真实 request_id、MemoryObj 身份和 pin/unpin 变化接起来；通用 Task 创建树不能自动建立共享块的请求归属。

Mooncake #4209：修正起因并定位完成通知缺口

后续评论和受影响 tag 的源码支持 TCP pump 漏投：请求 pump 已置位，而拒绝分支未投递执行。对应修复让投递不再依赖是否拒绝。受影响 tag 已在退役前从组表中移除旧组，因此不应将最初“CLOSED 组残留”的解释当作定论。

vLLM 0.29.0 的接收路径为每个 worker 创建 Task，并为每个请求记录 pull_tasks_count。process_pulling_result 只为 ok_reqs 递减计数并登记 finished_recving_reqs；err_reqs 仅记日志。ERROR 或异常路径记失败统计后返回。这提供了终态通知缺口的源码证据，尚不能证明完整调度器等待、空闲触发或 90 秒自恢复。
