Issue findings

Local observation
One PgJDBC42.7.13/JDK21.0.1 idle logical-replication read on private PostgreSQL17.1/test_decoding throws PSQLException55000: Tried to write to an inactive copy operation. The status interval is configured to3000ms and the stream reports closed. Target and JDI collector exit0; server shutdown is logged. Source review, artifact preparation, build and execution take166.89s.
What CoroPerf showed
CoroPerf joins the actual FutureTask constructor object1133 to four later diagnostic observations, recovering startChangefeed absent from the native/current exception stack. An explicit JDI resource observer binds that Task to stream1183 and CopyDual1184, independently checked against application-held Task/stream references. The same operation appears in the SocketTimeoutException, unlock entry, wrapped read failure and subsequent inactive-COPY failure. Seven timeout records are rethrows of one exception object1196, not seven timeouts. The source already documents the root cause; the additional evidence is historical ownership and the same-operation event sequence.
Scope and limits
The logical output plugin is test_decoding rather than wal2json, within the report explicitly described as plugin-agnostic. A real idle logical stream and unmodified42.7.13 driver are used, not physical replication or a thrown-error stand-in. A single controlled FutureTask supplies the component submission context; startChangefeed is its helper, not an original application registration. Resource identity requires the explicitly added observer and is not inferred from Task ancestry. Event-record order is captured, not physical timestamps; unlock is observed at entry, not exit. No duration, uninstrumented timing, alternate driver/plugin/interval or fix validation is claimed. Only one successful read workload ran.
