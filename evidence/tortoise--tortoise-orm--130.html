Issue findings

Local observation
The original create call committed its row. The subsequent get call with the same Python datetime raised DoesNotExist on 0.11.9. The database still contained the row. Across 354 invoice dates, the affected client missed all 412 expected invoices on equality lookup. Its one-day range queries also included 118 invoices from the following day. Version 0.11.10 returned every expected invoice on both query paths.
What CoroPerf showed
On the SQLite worker thread, the bound INSERT passed through adapt_datetime, which separated the date and time with a space. QuerySet.__await__ created a QuerySet._execute coroutine. Inside that same live instance, ValueWrapper.get_value_sql rendered the filter datetime with a T. SQLite compared the two stored and supplied strings. Converting only the filter input restored every result. Converting only the write input left the mismatch intact.
Scope and limits
The original Python, SQLite, ORM and aiosqlite versions ran locally on Linux. The additional invoice workload used 412 midnight timestamps from the Chinook sample database. Two explicit timestamps also exercise subsecond precision. SQLite DATETIME() truncated the fractional timestamp and selected the whole-second neighbour. The tests use timezone-naive datetimes.
