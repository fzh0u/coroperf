案例结论

本地复现结果
Ray 2.45.0 在 32 个并发 HTTP 流中各发送 64 个有序事件。逐事件跨部署转发需要 2048 次 Ray 结果交接，两种测试顺序下吞吐为每秒 3250–3476 个事件。首个事件立即发送，其余每 8 个一组后，交接降到 288 次，吞吐为每秒 8787–8802 个。生成器与入口同部署时，省去跨部署转发，吞吐约为每秒 9200 个。三种路径的事件内容和顺序一致。
CoroPerf 证据说明
两次读取经过同一个 Ray 结果包装器，物理执行栈完全相同。核对实际 DeploymentResponseGenerator、ActorReplicaResult 和所属的 Python 异步生成器帧，可以把读取接回 HTTP 响应体的创建位置。观测 1 接回记录 0 的 launch_lookup，观测 3 接回记录 2 的 launch_summary。反转客户端发起顺序后，相同执行栈分别归到交换后的路由。
适用范围与局限
实验使用本地 HTTP 入口、两个实际的 Serve 副本和合成 SSE 输出，两种测试顺序下每种配置各跑五次。吞吐按客户端收到的事件计数，分组会改变到达节奏。同部署对照用于隔离 Ray 2.45.0 上的跨部署转发开销。报告者在 HAProxy 和直接流式传输可用后关闭了 Issue，本次测试验证的是应用侧分组方案。
