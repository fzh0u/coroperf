案例结论

本地复现结果
两条流在 Ray 副本边界的首包都约为 46 毫秒。使用候选 PR #67968 时，交互式流在引擎侧约 5 毫秒，首包输出约 40 毫秒。批处理流在引擎侧约 33 毫秒，首包输出约 12 毫秒。原版在这个路径上没有候选 PR 新增的五类延迟观测。汇总 20 个具有相同模型标签的请求，拿 TTFT 的 p95 减去进入和输出开销各自的 p95，得到 5.2 毫秒。逐请求配对后再求引擎侧 p95，得到 33.4 毫秒。本地补丁直接记录引擎侧区间，对照测得的 p95 同为 33.4 毫秒。
CoroPerf 证据说明
两个首块进入实际 Batcher 队列时，执行栈完全相同。核对运行中的读取 Task、所属 Batcher 和同一个队列，把观测记录 4 与 5 分别接到创建记录 2 与 3。创建读取 Task 的请求 Task 再接回记录 0 与 1 的交互式和批处理入口。两条流分别核对了引擎送出、队列接收和调用方收到的同一个首块对象。原生 asyncio 调试记录相同的创建路径，缺少最初的发起入口。反转发起顺序仍能正确归属。
适用范围与局限
实验运行固定版本的 Ray LLMServer 流式处理、Batcher 和候选 PR 的 Ray Histogram 记录方法，使用本地模拟引擎和 45 毫秒批处理间隔。每个版本与发起顺序各运行五次，两条流使用同一个模型标签。分位数来自副本边界上的原始直方图观测。验证范围为该边界，模型执行和路由器、代理排队不在实验范围内。候选 PR 的 12 项上游测试均通过。本地补丁另核对引擎指标只在调用方收到首包时记录。Issue 和 PR 仍开放。
