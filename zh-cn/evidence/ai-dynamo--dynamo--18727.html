案例结论

本地复现结果
固定版本的 Dynamo Python 前端反复复制 token ID 前缀，vLLM 的 DeepSeek-R1 解析器会扫描此前的前缀以查找推理结束标记。每段包含一个推理 token 时，两种运行顺序下，8192 段的前端线程 CPU 时间中位数从 328–330 毫秒降到 120–121 毫秒，16384 段从 1097–1100 毫秒降到 243–245 毫秒。移除响应的 created 时间字段后，两边的逐段响应、最终文本和 token 统计均一致。候选 PR #18728 的 8 项前缀测试均通过。
CoroPerf 证据说明
两次解析观测在同一个事件循环线程上，物理执行栈相同。实际 Task 和异步生成器帧确认各自的后处理器，观测记录 4 接到创建记录 2，5 接到 3，两者都由同一个 dispatch 位置创建。核对同一个 asyncio Handle 和请求对象，再分别接到记录 0 的交互式发起入口和记录 1 的批处理入口。原生 asyncio 调试创建栈只回到 dispatch，缺少这两个入口。两个版本、两种发起顺序下均能正确归属。交互式请求调用解析器 66 次，批处理请求调用 258 次。
适用范围与局限
组件实验运行 Dynamo 原始的 _generate_and_stream、StreamingPostProcessor 和 vLLM 0.33.0 的 DeepSeek-R1 解析器，以进程内的预置 token 流驱动，并用实验接口替代实际解码。CPython 3.12.4 上记录消费完整流的线程 CPU 时间，每种顺序、每个版本先预热一次再测量五次。测试范围限于该前端组件及上述解析器。Issue 和候选 PR 仍开放。
