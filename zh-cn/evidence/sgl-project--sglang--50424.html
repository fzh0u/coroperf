案例结论

本地复现结果
两次并发基准运行各收到一个有效流和一个以 HTTP 200 开始、随后返回拒绝消息的流。报告版本和固定的 main 共计 4 个成功、21 个生成 token。候选 PR #50427 的分支，以及将同一修改应用到 main 的版本，均计为 2 个成功和 5 个 token。两条有效输出保持一致，两个被拒请求的输出 token 均计为 0，并保留原错误消息。
CoroPerf 证据说明
两个被拒请求的发送内容完全相同，在同一事件循环线程上从相同的 async_request_sglang_generate 执行栈返回。通过实际请求 Task 和 RequestFuncInput 核对执行与 benchmark 内的创建记录，再沿父 Task 接回 launch_evaluation 和 launch_calibration。返回的 RequestFuncOutput 与各自汇总函数收到的是同一对象。asyncio 调试模式记录了共同的创建位置，缺少这两个发起入口。反转发起顺序后仍能正确归属。
适用范围与局限
实验运行实际的 Python 基准函数与 HTTP 客户端，使用确定性的回环响应、预置输入和实验 tokenizer。对照核实的是吞吐量的 token 计数和请求成功统计。模型服务与实际模型分词不在本次实验范围内。Issue 和候选 PR 均仍开放。
