拼接补回了什么

实际等待上报的计时快照接回原调度栈，实际 Request 对象再把调度栈接回两个提交 Task。这样可以将后来随空跑回复一起上报的计时归到各自原始请求。

先看协程执行栈，再沿拼接点追溯创建栈和更早的调用者。各栈块保留原有帧顺序。

案例结论

本地复现结果
两条请求都调度了 3 个 prefill token，并返回同一个输出 token。在夹具提供的时钟下，旧版 EngineCore 对结果等待的计时为 2 和 0 毫秒。PR #61690 引入的 worker 计时根据两对流事件得到 28 和 12 毫秒。两条统计都在请求已返回后随同一个仅含统计的包送达，后续一个包只带有空跑的统计记录。
CoroPerf 证据说明
两次读取计时记录的物理栈完全相同。核对每条待上报记录里的实际调度快照，先接回对应的调度栈。再核对调度器所用的 Request 对象，接回提交它的 Task。交互请求沿 4 → 2 → 0 回溯，批量请求沿 5 → 3 → 1 回溯。反转提交顺序后，两条计时归属随之交换，token 计数和时钟输入一致。
适用范围与局限
CPU 对照运行固定版本的调度器、计时装饰器、空跑统计发布和前端异步队列读取。模型输出和事件时间戳由夹具提供，数字用于验证计时边界。实际 CUDA 计时需要启用迭代日志并使用受支持的执行配置。计时 PR 已合并，整体 RFC 仍开放。
