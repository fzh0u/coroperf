拼接补回了什么

案例结论

本地复现结果
在配置 1 个 worker 的 Tokio 多线程 runtime 上，60,000-token 请求开始序列化时唤醒另一条 Task。从通知到首次执行的中位数，原版为 541–550 微秒，采用 PR #9487 中单独的 block_in_place 改动后为 3.33–3.45 微秒。序列化结束前就得到执行的比例从 0/300 变为 300/300。两版 JSON 字节和返回的 token 数量一致。同批长请求自身的本地完成时间由 1.74–1.77 毫秒变为 1.79–1.85 毫秒。
CoroPerf 证据说明
去除静态符号表和调试段后，优化 ELF 中的两条原生地址栈完全相同。ELF+0x1d54ac 的指令调用 ELF+0x1c9ec0，ELF+0x1c9f41 的指令调用 ELF+0x1c6710。这两个目标与相邻的回溯帧一致。将执行时的 Tokio Task ID 与发起时的 JoinHandle ID 核对后，两条栈分别接回交互与批处理入口。交换发起顺序和请求长度后，请求 ID 仍在 JSON 正文、控制信封和请求头中一致。函数名来自机器码逐字节相同的带符号副本。
适用范围与局限
实验隔离了固定版本 AddressedPushRouter 的 JSON 序列化，使用本地请求接收器和真实的环回 TCP 响应流。计时轮关闭栈记录。Tokio 单线程 runtime 的两组对照均保留内联序列化，就绪任务均在序列化结束后才执行。测量范围为本地调度，原报告的多副本吞吐量超出范围。Issue 仍开放，PR #9487 关闭时未合并。已核对的主分支使用更新的编解码路径，其中 JSON 回退仍在原执行路径上编码。
