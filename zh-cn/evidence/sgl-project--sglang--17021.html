案例结论

本地复现结果
CPU 回放使历史接收协程等待的实际 PyZMQ 对象 Future 就绪。随后，两个真实分词调用在接收协程恢复前占用其事件循环线程。每组五次实验中，在事件循环线程上分词时，从就绪到恢复的中位数为 32.6 毫秒。把相同工作移到工作线程后为 0.050 毫秒。八条首 token 输出和两组分词结果一致。
CoroPerf 证据说明
用实际接收 Task 将 handle_loop 执行记录 5 拼回创建记录 0。再用各自的 Task 和输入对象，把相同的分词执行栈记录 3、4 分别接回提示词和图片说明的创建记录 1、2。实测两个分词区间都位于 Future 就绪与接收协程恢复之间。反转启动顺序并交换输入长度后，分词工作仍归到正确入口。
适用范围与局限
实验使用固定版本的 SGLang 接收代码、进程内 IPC 和两次受控的 BERT 分词工作。单独换用 PR #17069 的接收循环后，八条输出按 3、3、2 分发，恢复前仍等待约 32 毫秒。Issue 因不活跃关闭，PR 在合并前关闭。报告中的模型运行和生产延迟仍待单独验证。
