案例结论

本地复现结果
CPU runner 已加载 all-minilm 时，历史原版第一个 12 条文本请求在拿到 runner 后的耗时中位数为 134.3 毫秒，采用 PR #7424 的本地改版后为 100.1 毫秒。预热后的中位数为 101.0 和 96.8 毫秒。两种发起顺序中，首次加载前端词表耗时 26.8–27.5 毫秒。所有向量分量完全一致，候选版本每条文本多统计两个特殊 token。
CoroPerf 证据说明
批量目录请求和单条查询的 worker 具有相同的 Embedding 执行栈。实际 Go context 携带的同一个记录对象将 HTTP 请求及输入行传给 errgroup worker，文本指纹与前端分词记录及另一进程收到的 JSON 输入一致。执行记录 1 接回批量目录请求的创建记录 0，执行记录 3 接回单条查询的创建记录 2。首个请求在创建 worker 前完成前端词表加载及逐条分词。交换请求顺序后，加载开销归到单条查询。
适用范围与局限
使用真实的环回 /api/embed、历史 CPU runner 和上下文长度以内的普通文本。每次对照先用空请求加载 runner。每组首请求中位数来自 5 个独立进程，每种请求的预热中位数来自每版 35 次请求。候选改版按输入行分别写入计数。测试覆盖历史端点开销，候选版改变了 token 统计口径，原报告与 Sentence Transformers 的对比超出本次测量范围。Issue #7400 仍开放，PR #7424 关闭时未合并。
