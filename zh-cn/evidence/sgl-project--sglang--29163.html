案例结论

本地复现结果
四个并发的 Kimi-K2.5 输入各有 6,000 到 7,500 个 token，一起进入同一个线程池 WorkItem。原版对每个输入走 Python 分词路径，候选补丁改用直接 encode。预热后做十组配对计时，整批中位耗时从 141 毫秒降至 43 毫秒，token ID 完全一致。第二轮分别是 138 和 43 毫秒。
CoroPerf 证据说明
四次 _encode_plus 的工作线程栈完全相同。实际运行的 WorkItem 里有同一个输入对象，批次又将这个输入和请求入队时记录的同一个结果 Future 放在同一位置。因此能找到正在等结果的 Task 及其发起栈。所选执行记录 8 和 9 分别接回批处理提交记录 4 和 5，再接到请求创建记录 0 和 1。
适用范围与局限
这是 CPU 上真实 tokenizer 和批处理组件的耗时，未运行模型推理。核对的主线提交和 PR 基准使用同一份批处理代码。Issue 和 PR 均因不活跃关闭。候选补丁对默认调用保留 TokenizerManager 使用的 token ID，同时省略原版返回的 attention_mask 字段。显式请求截断和 attention_mask 时，两版在本地对照中结果一致。
