案例结论

本地复现结果
两个异步写入 Task 执行同一条 SQL。两个独立 Task 读缓存时，原来的写入 Task 对象都已回收。2.1.5 上两次读取抛出完全相同的 TypeError，异常栈也相同。协程起源和 tracemalloc 指向 FrozenResult 内同一处 fetchall 分配位置，读取 Task 的创建栈只能追到共享的调度入口。
CoroPerf 证据说明
写入与读取两端观测到同一个 FrozenResult 及其内容。用实际结果对象的身份，将各读取 Task 的创建栈接回写入 Task 的创建栈。页面中的 1 → 17 → 20 和 2 → 18 → 22 分别恢复 start_import 和 start_refresh。在上游修复版本中，两个读取 Task 都成功返回同样的两行数据。
适用范围与局限
这是原帖 Core 流式查询示例的双写入、双读取扩展，使用 CPython 3.12.3 和 SQLite。比较 SQLAlchemy 2.1.5 与标记为 2.1.6 的已归档主线修复。两批共核对 32 条缓存交接，其中 16 条读取失败、16 条读取成功。去掉结果对象关系后，读取执行栈只能接回共享的读取调度入口。
