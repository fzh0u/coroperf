拼接补回了什么

实际 Tokio Task 和注册通知对象把相同的计时器执行栈接回两次 worker 注册，区分了等待首次检查的 worker 和需要额外重试的 worker。

先看协程执行栈，再沿拼接点追溯创建栈和更早的调用者。各栈块保留原有帧顺序。

案例结论

本地复现结果
空闲检查间隔设为 2 秒时，首次检查成功的 worker 从注册到就绪的时间中位数由 2003–2005 毫秒降至 5.1–5.2 毫秒。首次失败一次的 worker 由约 4007 毫秒降至 1006–1008 毫秒。默认 10 秒配置另做了一组对照，首次成功的 worker 从 10.004 秒降至 4.8 毫秒，需重试的 worker 从 20.005 秒降至 1.004 秒。在所有对照中，首次失败后端点仍为未就绪。
CoroPerf 证据说明
两次计时器到期的原生执行栈相同，两条 Task 的创建栈也相同。运行中的 Tokio Task ID 与创建时 JoinHandle 的 ID 一致，使执行记录 4 接到创建记录 2，5 接到 3。再通过端点注册时的同一个 Arc<Notify>，把共同的创建位置分别接到交互式和批处理注册记录 0 与 1。两个版本都反转注册顺序核对归属。拼接区分了使用同一执行路径的两个 worker，其中一个首次检查成功，另一个必须重试。
适用范围与局限
组件实验运行原始 Rust DistributedRuntime 和健康检查管理器，使用本地模拟引擎及内存发现服务。计时为单 Tokio 线程上从注册到首次观测到就绪的时长。2 秒配置下每种顺序和版本测三次，计时轮关闭栈采集。10 秒配置仅做一组对照。实验覆盖端点就绪状态，未包含模型加载或 Kubernetes 探针耗时。上游健康检查套件使用回环 QUIC 测试环境，基准版本 13 项、候选版本 16 项均通过。Issue 和 PR 仍开放。
