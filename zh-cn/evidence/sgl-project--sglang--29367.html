拼接补回了什么

从两条相同的 SGLang 结果交付栈分别拼回各自接收任务的创建入口。实际 IPC 端点和 Event 找到等待该结果的请求，请求的执行栈也独立拼回其创建记录。

先看协程执行栈，再沿拼接点追溯创建栈和更早的调用者。各栈块保留原有帧顺序。

案例结论

本地复现结果
启用 skip_tokenizer_init 并配置两个分词 worker 时，修复前只保留一个 worker，两个结果都由同一个实际接收 Task 交付。合并 PR #30682 后保留两个 worker，两个实际 TokenizerManager 接收 Task 通过不同的 Unix IPC 端点交付各自的结果。两个版本均保留原始 token ID，反分词 worker 的配置数均为一。
CoroPerf 证据说明
两个接收观测的 SGLang 执行栈相同。核对实际 Task、协程和 manager 后，把交互请求的接收记录 6 拼回创建记录 0，把批处理请求的接收记录 4 拼回创建记录 1。每个 manager 唤醒的正是对应请求在等待的 Event，再把交互请求执行记录 7 拼回创建记录 2，把批处理请求执行记录 5 拼回创建记录 3。即使调度器数据包将批处理结果排在前面，也能按请求 ID 和 IPC 端点恢复正确归属。
适用范围与局限
CPU 实验运行固定版本的 SGLang 配置、调度器发送、路由和接收方法。测试程序构造调度器输出，并创建接收和请求 Task。实验验证 worker 数量和结果路由的变化。完整服务启动、Rust 前端集成和生产吞吐量仍待验证。
