案例结论

本地复现结果
两个读取 Task 等在同一个 read_payload 调用点。代表性对照中，cProfile 把它们记为同一个函数条目，共 4 次进入，累计执行约 0.5 毫秒。CPython 3.15.2 的异步墙钟采样区分出两个等待中的 Task，分别得到 65 和 245 个样本。两个 Task 的创建栈都只到共同的 dispatch 回调，采样等待链也没有最初发起者。
CoroPerf 证据说明
采集器按同一个 Task 和实际的 StreamReader Future 测量挂起到恢复的时长。创建 Task 时，探针识别正在执行 dispatch 的实际 Handle，再沿它找回调度栈。记录 0 → 2 → 4 将 65.9 毫秒接回 launch_inventory。记录 1 → 3 → 5 将 245.6 毫秒接回 launch_profile。去掉 Handle 关系，两条观测只能追到共同的 dispatch。
适用范围与局限
在 Linux 上使用 CPython 3.10.4 和 3.15.2，通过本地套接字传输相同数据。独立发送线程控制两种延迟。两批实验独立交换发起顺序和延迟分配，共验证 32 条归因。时长为每个 Task 从挂起到恢复的时间，包含 I/O 就绪后可能发生的调度等待。
