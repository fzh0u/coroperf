案例结论

本地复现结果
使用 Kimi-K2-Thinking tokenizer 和 Transformers 5.3.0 时，连续三个各含 1024 行的增量解码包，在旧默认配置下耗时 4.27–4.37 秒线程 CPU 时间。采用 PR #23409 默认开启的缓存后，中位数降至 51.7–52.2 毫秒。128 行的中位数从 530–547 毫秒降至 6.43–6.48 毫秒。所有文本片段和输出 token ID 均一致。在原版显式开启缓存、在合入版显式关闭缓存，分别复现了对应的耗时。关闭特殊 token 过滤的 128 行对照在两版中都约 5 毫秒。
CoroPerf 证据说明
一个解码线程上出现两条相同的执行栈，分别属于同一调度数据包中的两行。核对实际 token 列表的位置，再通过该行的请求 ID，将执行记录 2 和 3 接回前端 Task 创建记录 0 和 1。两条 Task 均经实际 ZeroMQ IPC 和 TokenizerManager 响应路径收到预期结果。反转发起顺序及包内行顺序后仍能正确归属。旧版每行调用原始 all_special_ids 属性计算 20 次，缓存预热后每行省去这 20 次计算。
适用范围与局限
CPU 实验使用固定版本的解码组件、官方 Kimi tokenizer 和预置增量 token ID。每种默认配置和测试顺序先预热一次，再测五次，计时包含三个解码包的增量文本处理。拼接证据来自两行的本地 IPC 实验及实际前端响应协程。本次测量针对解码组件。上游报告关注更大规模 GPU 部署的客户端 token 间延迟。Issue 已关闭，默认配置改动已合入。
