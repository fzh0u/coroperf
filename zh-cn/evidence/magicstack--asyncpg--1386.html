案例结论

本地复现结果
asyncpg0.32.0、CPython3.14.3、私有 PostgreSQL17.1 一次运行原始忙查询示例：SELECT pg_sleep(0.5) 占用连接，使并发 BEGIN 抛出 InterfaceError。查询结束后连接仍打开且服务端无事务，但 _top_xact 仍指向该 FAILED Transaction；后续事务发送 SAVEPOINT，得到原生 NoActiveSQLTransactionError、SQLSTATE25P01。进程退出0，连接和数据库清理完成。含选择、源码、准备和运行115.05秒。
CoroPerf 证据说明
API 实际返回的忙 Task 对象0x73927aac5a90 与独立的原生等待快照、Coroperf 身份一致。选取的活动采样早于 BEGIN 失败，同一任务在后续 SAVEPOINT 错误前正常返回。CoroPerf 把创建2接到等待采样40，恢复原生 Task 栈和两个错误回溯都缺失的 launch_busy_query。额外 API 观察把该任务、Connection0x73927aa75150 和失败 Transaction0x73927a86e110 关联到两次失败。报告已说明 stale _top_xact，新增诊断事实是实际占用连接的操作及其历史提交上下文。
适用范围与局限
这是原始并发查询造成的发送前 BEGIN 失败组件，不是 Aurora/RDS Proxy、SQLAlchemy、pool 或取消 BEGIN 的变体。保持原始 Task 结构：launch_busy_query 只给既有 create_task 表达式命名，后续事务仍在 main 内直接执行。资源身份依赖额外 API 观察，不能从通用 Task 祖先关系推断共享 Connection/Transaction 所有权。原生等待栈仅有 execute，Python continuation 检查止于不透明的 Cython protocol awaiter。成功场景一次，没有 reset/修复、pool、proxy、取消变体、其他版本或额外批次。
