拼接补回了什么

相同的内部请求 ID 将两条相同的分词执行栈分别接回对应的 Tokio HTTP Task。HTTP 请求与响应中的公开 ID 再接到最初的发起入口，区分每次排队等待属于哪个调用方。

先看协程执行栈，再沿拼接点追溯创建栈和更早的调用者。各栈块保留原有帧顺序。

案例结论

本地复现结果
每轮由 Rust HTTP 前端处理 8 条普通文本请求，每条 8070 个 token。原版只有一个分词线程，两种发起顺序下，每轮最慢排队时间的中位数为 102.7–103.1 毫秒。候选 PR 在 8 核前端自动启动 4 个分词线程，把中位数降至 12.5–12.7 毫秒。原版手动配置 4 个分词线程时，同样为 12.5–12.7 毫秒。候选 PR 使整轮分词区间从 125.5–125.7 毫秒降至 34.7–35.3 毫秒。每条请求分词本身仍约为 16 毫秒，所有对照下调度器收到的 token ID 逐一一致。
CoroPerf 证据说明
单线程原版中的两条原生分词执行栈完全相同。用完整的内部请求 ID，把每次工作线程出队接回同一请求的入队、Tokio HTTP Task 和调度器输入。执行记录 3 和 5 分别接到请求创建记录 2 和 4。再用本地 HTTP 请求发出、服务端响应返回的公开 ID，接回记录 0 和 1 的原始入口。反转发起顺序后，两条拼接仍然正确。原版四线程对照表明，改善来自分词并行后排队缩短。
适用范围与局限
本地回环实验使用固定版本的 SGLang Rust HTTP 前端、TokenizerManager、原生分词线程池和调度器环形队列。它用官方 Gemma 4 31B 指令模型的 tokenizer，经 /generate 接收纯文本，由调度器夹具为每条请求返回真实 token ID。每种配置与顺序先预热一次，再计时五轮。双请求调用栈在单独一轮采集。服务端、处理器和实际分词依赖以优化等级 2 构建，保留调试信息。计时从分词入队开始，到工作线程取出请求或完成编码为止。上游报告关注 GPU 部署下的客户端延迟。候选 PR 的线程数单元测试已在本地通过。Issue 与 PR 均开放。
