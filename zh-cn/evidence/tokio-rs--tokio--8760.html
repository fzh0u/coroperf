案例结论

本地复现结果
在 2,048 个任务分别使用 10 ms interval 的负载下，两批本地实验中，Tokio 1.53.1 的进程 CPU 时间中位数比 1.52.4 高 22–25%。上游修复比它的父提交低 16–22%。在单独的探针实验中，两个发起入口的原生 spawn 位置相同，修复前每轮的 384 次定时器清理也只有一种物理函数栈。
CoroPerf 证据说明
CoroPerf 用工作线程上的活跃 poll 区间确定采样属于哪个 Task，再拼回其创建栈。区间 158–166 支撑从记录 34 到 159 的拼接，恢复 launch_profile。区间 160–238 支撑从记录 76 到 161 的拼接，恢复 launch_inventory。两种启动顺序下的 768 次观测都与独立记录的 Task ID 和返回的 JoinHandle 一致。两轮修复版对照在 tick poll 内都记录到 0 次清理。
适用范围与局限
这是 Linux x86-64 上的受控改编，使用四个工作线程和 parking_lot。CPU 比较来自未加探针的版本。单独的双调用者实验用 32 个 interval，在修复及其父提交的 clear_entry 中加探针，统计每次 tick poll 内的清理。最后销毁定时器发生在统计区间外。
