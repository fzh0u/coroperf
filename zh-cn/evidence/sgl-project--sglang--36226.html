案例结论

本地复现结果
报告版本与核对的主分支版本使用相同的两段式元数据遍历。32 个积压块中，两个元数据字段到最后四分之一才出现时，本地补丁把每次合并的线程 CPU 时间中位数从 17.0–17.8 微秒降到 9.18–9.81 微秒。每块都包含五个标准字段时，从 22.4–23.2 微秒降到 15.2–16.4 微秒。20 种测量输入的输出内容和元数据键顺序均一致。
CoroPerf 证据说明
两次合并的执行栈相同。核对实际 Task、通知 Event 和取出的输出列表后，执行记录 2 和 3 分别接回交互式与批处理发起记录 0 和 1。批处理入口对应 32 个带逐 token 注释的积压块，交互式入口对应 2 个没有增量元数据字段的积压块。交换积压归属与发起顺序后，处理开销归到交互式请求，执行栈的形状相同。
适用范围与局限
实验只覆盖原报告中的流式积压处理。拼接使用固定版本的 SGLang 前端方法和预置解码数据包，在同一轮事件循环内送入积压块。线程 CPU 时间另行测量，每个哈希种子测 7 轮，每轮调用 3000 次。GPU 推理、HTTP 传输及客户端延迟均超出本次实验范围。GitHub 因长期无活动关闭 Issue。已核对的主分支提交仍保留原实现，对照使用本地补丁。
