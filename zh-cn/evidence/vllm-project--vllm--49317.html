拼接补回了什么

两条相同的图像预处理栈属于不同的 generate 请求。原版用实际 Task 找回两个入口，修复后用实际执行器 WorkItem 跨线程找回同样的两个入口。

案例结论

本地复现结果
两条直接调用 AsyncLLM.generate 的请求分别用实际 Qwen2-VL 图像处理器处理一张和三张图片。原版的两次处理都在事件循环上执行。合并 PR #49608 后，两次处理都移到一个 renderer 工作线程。两版各跑七次预热后的实验，在两条请求启动后立即入队的回调，延迟中位数从 30.3 毫秒降到 0.135 毫秒。两版生成的提示词 token ID、图像网格元数据和像素张量一致。
CoroPerf 证据说明
每个版本内，两次图像预处理的执行栈完全相同。原版按当前实际 Task 将图片说明和相关性请求分别拼回 2 → 0 和 3 → 1。修复后，在提交和执行时核对同一个 WorkItem，分别拼回 8 → 6 → 4 和 9 → 7 → 5。由此找回工作线程栈里缺失的应用入口，并与 InputProcessor 里看到的请求 ID 交叉核对。
