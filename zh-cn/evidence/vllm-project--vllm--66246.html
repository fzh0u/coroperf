案例结论

本地复现结果
Completion、Chat Completion 和 Responses 三个后端都复现了问题。报告版本和所核对的主分支上，探针与主负载均发出 64 token 的上限。单条请求覆盖为 17 时，两者均发出 17。分别在 PR #66260 的提交和已应用该 PR 的主分支上验证后，探针两种情况下均发出 1，主负载保持 64 或 17，temperature 也保留。四个版本共完成 48 次基准运行。
CoroPerf 证据说明
主分支上的两条 Chat Completion 请求，POST 请求体和响应接收栈完全相同。CoroPerf 在 ClientRequest.send 记录实际的 ResponseHandler 和发出请求的 asyncio Task。观测记录 1 通过该对象接回探针 Task 的创建记录 0，观测记录 3 通过同一关系接回主负载 Task 的创建记录 2。由此确认本应只请求 1 token 的探针发出了 64 token 的上限，即使请求体没有区分角色的标记。
适用范围与局限
实验运行 benchmark() 的原有调度和 HTTP 客户端。本机回环服务固定返回一个 token，用来核对实际请求的上限及所属任务。模型生成耗时和端到端推理吞吐量未测量。GitHub issue 与修复 PR 均仍开放。
