案例结论

本地复现结果
受影响 client 提交99356800 的一次真实事务入口取消，使连接保留事务深度1/INTRANS。后续事务上下文正常退出，但同一 Connection 看见1行 INSERT，独立 Connection 看见0行；显式 rollback 抛出 ProgrammingError。成功进程退出0，连接、表和私有 PostgreSQL 均清理。后续批次从开始到成功28.79秒；同批更早的一次观察器失败发生在取消之前。
CoroPerf 证据说明
通用 CoroPerf Task 创建与文件范围取消异常观察恢复 launch_interrupted_entry，后续事务退出后的 API 边界观察恢复 launch_reuse_check。两个辅助入口均不在当前观察栈中，而在 causal 栈中恢复。额外的 Connection/Task 观察把取消入口任务、后续复用任务与 rollback 失败独立接到同一真实 Connection，跨阶段记录到深度1/INTRANS。目录选取3→5、29→31两条创建关联。稍后的清理 Task 复用了复用任务的对象地址，但运行时 generation 不同，没有把两者记录混在一起。
适用范围与局限
准确 client 源码99356800e90aa0e7b604f652d714ef0f33422b47 使用缓存 CPython3.14.3、PostgreSQL17.1 和 pure-Python libpq，原报告为3.14.8/18.4。checkout 从已安装发行元数据读取3.3.9，不代表验证了发行版3.3.9。Connection 与上下文管理器 wrapper 身份依赖额外 API 观察，不能从 Task 父子关系推断共享资源，也没有捕获隐藏的 AsyncTransaction 对象身份。提交辅助函数为此独立 harness 增加。报告已说明事务栈清理根因，新增证据是历史 caller 与跨阶段资源状态。保留 b14、b15 各一次取消前的观察器失败；成功场景仅一次，未测嵌套 savepoint、多服务器/实现/版本、修复或重放。 此归因组件把后续复用块放入独立 Task，原报告是在 main 内直接执行；不声称复现原生产任务结构。
