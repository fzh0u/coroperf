拼接补回了什么

通过实际 worker Task，把相同的重复计数栈接回两次 HTTP 提交所创建的批次 Task。用同一个批次对象确认每次重复扫描属于评估批次还是索引批次。

先看协程执行栈，再沿拼接点追溯创建栈和更早的调用者。各栈块保留原有帧顺序。

案例结论

本地复现结果
处理 1024 条时，原版计数 1025 次，共访问 525824 条历史结果，包含结束时的最后一次重计。PR #22280 对 1024 条结果逐条更新计数，省去历史扫描。两种测试顺序中，从环回 HTTP 提交到批次结束的事件循环线程 CPU 中位数由 235–256 毫秒降至 20.4–21.3 毫秒。两版返回相同的 930 个成功结果和 94 个模拟单条失败。候选补丁在批次结束后才公布结果 URL。
CoroPerf 证据说明
两个 HTTP 提交已返回，两条 worker 的 _recount 执行栈仍相同。通过实际运行的 asyncio Task 和同一个批次对象，把执行记录 8 接回 worker 创建记录 1，再用当时活跃的父批次 Task 接回评估请求的 HTTP 创建记录 0。索引请求的路径是 9 → 4 → 3。反转 POST 顺序后两条路径仍正确。原版追踪中，两条的评估批次访问历史结果五次，四条的索引批次访问十四次。
适用范围与局限
实验使用固定版本的批次存储、协议模型和路由方法，通过真实环回 HTTP 调用，单条推理由测试替身返回。每种规模、版本和运行顺序各测 7 次，计时轮关闭栈采集。1024 条时的遍历次数另行记录。取消操作的最终结果一致。候选版通过 30 项上游测试，其中两项新增断言在原版上失败。GPU 推理超出本次测量范围。核对时主分支的批次存储文件与 PR 基线相同，Issue 和 PR 均开放。
