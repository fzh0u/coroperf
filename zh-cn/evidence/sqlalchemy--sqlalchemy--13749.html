案例结论

本地复现结果
240 次有界、无需数据库的队列组件对照，在 CPython 3.11.18 的 SQLAlchemy 2.0.55、2.1.6 上复现取消丢失。原生 cancelling() 已能显示缺陷。另设应用扩展：两个取消 Task 从不同入口创建，在事后观察目标前均被回收。两个目标的原生栈、创建栈、协程起源和分配栈相同，均未保留历史取消入口。
CoroPerf 证据说明
profile 事件记录实际 C Task.cancel 接收对象与取消计数递增，将每次已接受的请求绑定到当时运行的发起 Task；弱生命周期记录确认其已回收。coroPerf 把历史取消调用采样接回同一发起 Task 的创建，恢复 start_deadline_cancel 或 start_shutdown_cancel。两个独立批次交换两种启动顺序，共核对 48 个历史来源：受影响版本 32 个、修复版 16 个。取消来源单独保存为因果关系，不冒充目标 Task 的创建祖先。
适用范围与局限
组件对照通过 greenlet_spawn 调用真实发布版 AsyncAdaptedQueue，不使用 DBAPI 或数据库。历史来源扩展增加了观察 gate，与上游原程序分开。Python 3.11 的 SQLAlchemy 2.0.56，以及 Python 3.12.16 的两个旧版本均通过组件修复对照；未测试 2.1.7 或 Python 3.10 及更早版本。原生与采集模式的应用结果一致。删除取消历史或 Task 创建记录后均无法归属。SQLAlchemy、greenlet 的全部 Python 与原生文件均与通过哈希校验的官方 PyPI wheel 相同。原生标志已可识别取消丢失；coroPerf 补充历史发起者身份，不声称发现根因或提供新修复。未测生产开销。
