拼接补回了什么

先看协程执行栈，再沿拼接点追溯创建栈和更早的调用者。各栈块保留原有帧顺序。

案例结论

本地复现结果
v0.29.0 和所核对的主分支在单客户端、两个活跃对话下应发 4 次，实际发出 3 次。双客户端处理四个三轮对话时，应发 12 次，实际发出 10 次。进程都以状态码 0 退出。本机收到的每一个对话和轮次都与导出的统计一致。PR #57181 补齐了应发的轮次，并保留显式设置的 2 次请求上限。
CoroPerf 证据说明
两个客户端的响应回调栈完全相同，退出栈也完全相同。用 aiohttp 的实际 ResponseHandler 把接收记录 2、6 接回发送 Task。退出记录 3、7 来自这两个 Task 本身。再用子进程 PID 和客户端编号，将 Task 创建记录 1、5 接回主进程启动记录 0、4。真实队列和本地对话对象显示，两边都在取到队列结束标记后退出，各留下一次未发的第三轮用户请求，请求失败数为零。
适用范围与局限
实验在 Linux 本机运行完整基准 CLI、进程间队列、aiohttp 客户端和统计导出，并使用本地分词器及固定 SSE 响应。跟踪使用 Python 的 spawn 方式，子进程原始栈不含主进程的发起帧。未测真实模型的推理吞吐。Issue 和 PR #57181 仍开放。单独应用处理结果队列的 PR #69282 时，最小场景仍只发出 3 次。
