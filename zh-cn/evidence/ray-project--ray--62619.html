拼接补回了什么

实际指标汇报 Task 和跨线程调度的同一个 asyncio Handle，把两条相同的指标刷新栈分别接回部署句柄的初始化。与共享汇报任务对照后，可将原版增加的路由线程 CPU 开销归到逐句柄唤醒。

先看协程执行栈，再沿拼接点追溯创建栈和更早的调用者。各栈块保留原有帧顺序。

案例结论

本地复现结果
原版为每个部署句柄创建一个缓存指标汇报 Task，候选 PR 则在路由事件循环上运行一个共享 Task。128 个空闲句柄使用默认的 100 毫秒汇报间隔时，两种顺序下，每个 850 毫秒窗口的路由线程 CPU 时间中位数从 40.3–42.2 毫秒降至 17.3 毫秒，减少 57–59%。无句柄时低于 0.13 毫秒。独立的 16 句柄对照中，首轮汇报从唤醒 16 个 Task 减到 1 个，两个版本都刷新了 16 次，逐句柄计数增量一致。
CoroPerf 证据说明
原版的两次指标刷新在路由线程上经过完全相同的执行栈。用各自 RouterMetricsManager 保存的实际 Task，把执行记录 4 和 5 分别接回创建记录 1 和 3。创建发生时正在运行 call_soon_threadsafe 返回的同一个 asyncio Handle，沿它跨线程接回记录 0 或 2 中的 DeploymentHandle.options 初始化，区分使用同一部署的聊天和嵌入调用者。原生 asyncio Task 调试栈只记录共用的路由侧回调。反转初始化顺序后仍能正确归属。候选 PR 中，两个管理器由同一个 Task 汇报，仍可沿实际注册回调接回各自入口。
适用范围与局限
组件对照在 Ray 2.59.0 中使用固定版本的 router.py，运行实际 DeploymentHandle.options、路由线程初始化、缓存指标代码和 Ray 指标调用。控制器通信使用本地夹具。每种配置和顺序预热后测五个空闲窗口。唤醒次数与拼接栈由单独实验采集。计时范围为缓存句柄所在的路由线程。模型推理和外部 Prometheus 抓取在实验范围之外。候选 PR 通过六项上游测试。另一个生命周期对照发现，最后一个旧句柄关闭与新句柄注册交叠时，候选 PR 会留下两个汇报任务。本地补丁在两种注册顺序下均维持一个任务，两个句柄的计数增量一致，也通过上述六项测试。Issue 与 PR 均开放。
