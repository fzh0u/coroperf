拼接补回了什么

完整 ADD 消息和实际入队的 Request 对象将两条相同的调度器观测接回交互与批量 Task 的创建栈。两条请求都在本次调度之后、等待计数生成之前到达。

先看协程执行栈，再沿拼接点追溯创建栈和更早的调用者。各栈块保留原有帧顺序。

案例结论

本地复现结果
一个名额已被占用，另有一个请求已被调度器检查过并继续等待。两个新请求在本轮模型结果返回前入队。原版将容量等待数报为 3。PR #68700 将这一轮报为 1。下一次调度仍无法接纳这三个请求时，容量等待数恢复为 3。两版的实际队列计数始终都是 1 个运行、3 个排队。两条协程反向提交，计数相同。
CoroPerf 证据说明
两个请求进入 Scheduler.add_request 时的执行栈完全相同，前端 Task 当时已经结束。先核对 vLLM 客户端发出和本地接收的完整 ADD 消息，再按实际 Request 对象匹配输入队列和调度器。交互请求沿记录 4 → 2 → 0 回到创建栈，批量请求沿 5 → 3 → 1 回溯。这两条拼接说明了在 schedule() 之后、统计生成之前入队的请求各来自哪里。
适用范围与局限
CPU 对照运行 vLLM 的异步提交、请求预处理、引擎输入处理和调度器。跨边界传输使用进程内 ZeroMQ，模型结果由夹具提供。实验范围限于这些组件。线上报告中的张量并行、HTTP 指标抓取和网关仍待验证。Issue 和 PR 均开放。
