案例结论

本地复现结果
后端取走首批并处于受控暂停期间，默认容量已能预取 1 批，本地选项设为 4 后可预取 4 批。两种发起顺序下，每条流水线均返回相同的 7 个 embedding。真实 CPU 路由器中，容量 4 在单请求批次下吞吐略有提高，在最多 4 个请求一批时吞吐略有下降。两种对照中，向量与默认配置及原版一致。
CoroPerf 证据说明
两条批处理任务申请通道空位时均返回 Pending，并且在同一个 Tokio 线程上得到完全相同的原生执行栈。用实际 Task ID 和发送通道把观测接回各自的创建位置，再沿实际初始化 Task 接回 launch_catalog 或 launch_search。反转发起顺序后，同样两条执行栈的归属随之交换。
适用范围与局限
栈采集实验在后端取走首批后有意暂停，并运行真实 Candle CPU 模型。耗时来自另一组无插桩的回环测试，使用 bge-micro 和两种 token 预算，结论适用于测试的 CPU 工作负载。容量选项已在本地测试，GitHub Issue 仍开放。
