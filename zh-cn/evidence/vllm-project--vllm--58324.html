案例结论

本地复现结果
在同一轮调度里，64 个音频片段的会话重复复制 63 个已处理特征，4 个片段的会话复制 3 个。请求级前缀缓存让每个会话只复制 1 个。两种顺序下，两个会话均保持原有的 64 条和 4 条输出增量。历史从 1024 个特征开始时，关闭采集后单次 NewRequestData.from_request 的 CPU 时间中位数从 1.36–1.38 毫秒降到 6.66–6.82 微秒。
CoroPerf 证据说明
记录 4 和 5 来自同一次 Scheduler.schedule，执行栈完全相同。NewRequestData.from_request 中的 Request 与首次进入调度器时是同一个对象。首次提交的活跃 asyncio.Task 与 RealtimeConnection.start_generation 创建的 Task 及其协程一致。4 → 3 → 1 接回实时字幕，5 → 2 → 0 接回实时笔记。交换长短会话的发起入口后，复制次数随对应会话交换。
适用范围与局限
CPU 实验运行真实的 vLLM 生成 Task、流式调度器和请求转换，通过进程内队列提供合成音频特征与预设模型输出。计时只覆盖请求转换，每步仍向 worker 提供完整特征列表。Issue #58324 和 PR #58334 均开放。PR 应用到主分支 31814a6f6f2d 后，写入带 slots 的特征对象时引发 AttributeError。已验证的本地适配把前缀缓存保存在可续传的 Request 上。
