案例结论

本地复现结果
CPython 3.10.3 在 release 时确实把已经排队的任务对应的 Future 设为就绪，但下一次许可仍由原持有者取得，先排队的任务继续等待。在本实验中，3.10.4 和 3.14.3 都把许可交给了先排队的任务。回调执行后，Task 栈、调试创建栈和协程起源都缺少两个原始发起者。3.14.3 的原生调用图能显示当前等待位置。
CoroPerf 证据说明
CoroPerf 记录 release 实际唤醒的 Future，以及实际获得下一次许可的 Task。下方许可栈接回该 Task 的创建栈，再沿匹配的回调 Handle 找到 launch_profile。仍在等待的 Task 通过自己的 Handle 接回 launch_inventory。移除 Handle 边后，两条链都只能回到共享的 dispatch。
适用范围与局限
页面展示 Linux 上 CPython 3.10.3 的双任务受控实验，并在 3.10.4 和 3.14.3 运行相同对照。实验使用一个许可，最后让两个任务正常完成。
