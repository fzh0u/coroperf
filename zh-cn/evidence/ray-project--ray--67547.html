调用栈证据

拼接补回了什么

把已就绪却读取零字节的生成器接回登记位置。Ray 原生任务 ID 将它接到 actor 的 asyncio.Task，算子身份将它接回训练或验证迭代器的发起位置。

先看协程执行栈，再沿拼接点追溯创建栈和更早的调用者。各栈块保留原有帧顺序。

案例结论

本地复现结果
原版和补丁版各运行 12 次本机对照。消费者暂停约 600 毫秒时，Ray 2.59.0 的调度次数中位数约为 1054，执行器线程 CPU 为 600 毫秒。应用开放的 PR #67572 后，两项中位数降到 135 次和 279 毫秒。两组每次都按序交付 131072 行。暂停后的同一段 NumPy 运算的耗时中位数从 213.2 毫秒降到 13.9 毫秒。
CoroPerf 证据说明
驱动端记录 2 和 7 的轮询栈完全相同，实际读取均为零。用同一个 ObjectRefGenerator 把 ray.wait 返回的就绪对象接回驱动端创建记录。Ray 原生任务 ID 和 TaskContext 编号又把这份记录接到 actor 中实际创建的 asyncio.Task。actor 恢复记录 4、9 分别接回该 Task，并继续回溯到训练和验证数据集各自的发起位置。
适用范围与局限
实验通过单节点、纯 CPU 的公开 iter_batches 接口运行，使用普通内存数据和约 600 毫秒的受控消费者暂停。线程 CPU 和 NumPy 耗时在关闭跨进程跟踪时测得。应用补丁后仍有调度开销。运行验证使用 Ray 2.59.0 官方 wheel 加上 PR 的原始调度改动。Issue 和 PR 均仍开放。
