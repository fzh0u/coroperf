拼接补回了什么

两条最终异常栈都指向流清理。首次抛出时保留的栈指出两个真正失败的读取，再拼回各自的 Task 创建栈，就能确定不同的发起者。

栈帧保留在各自的采集块中。拼接点表示两个采集块之间有可核实的关系。拼接栈里的实例标签取自该实例在本次采集中首次出现的记录号。

案例结论

本地复现结果
两条 loopback TCP 连接分别使不同的读取失败，错误文本相同。两个 Task 结束后的异常栈都变成 session → wait_closed → socket 接收。调试创建栈还能显示发起者，Task.get_stack() 和带局部变量的最终 traceback 都缺失真正失败的读取。省略第二次 await 后，两条读取栈均保留。
CoroPerf 证据说明
CoroPerf 的文件范围异常探针在清理前保存 _wait_for_data 的首次抛出现场，并用同一 Task 的标识接回创建栈。页面中，记录 5 → 19 找回 launch_profile 的 readexactly，记录 10 → 13 找回 launch_inventory 的 readuntil。随后同一批 Task 的记录 22 和 16 分别出现 wait_closed。核验独立核对返回 Task 的协程对象、两次捕获时间和清理时重复抛出的同一异常对象。
适用范围与局限
在 Linux 上用 CPython 3.12.4 和 3.14.3 运行原单连接程序和受控的双连接实验。3.14.3 的实时调用图能显示仍在等待的读取，拼接保留的是故障结束后需要的历史信息。两种启动顺序和两种读取分配共 16 条首次抛出拼接均通过核对。
