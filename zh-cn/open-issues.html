Asio #1720上游 issueC++ / stackless

最后一次 socket write 为什么不再完成？

CoroPerf 已补充的定位证据
CoroPerf 的二进制探针和既有实例图区分同一 frame 地址的多次寿命，并接回 writer。可选激活区间补足仅指令展开缺失的创建者证据；新增 Asio do_init 的 frame／handle 观察，把每次 write 接到正确的存活代次，再用 reactor 事件区分“操作仍排队”和“已完成却未恢复”。

展开证据与验证计划
已有证据
流式 send 返回 EPIPE、传输零字节。reactive_socket_send_op_base 将零字节错误当作成功短写，返回 done_and_exhausted，关闭 try_speculative_。在边沿触发的 descriptor 已注册 EPOLLOUT 后，下一次 write 直接排队，既未尝试 send 也未改变注册，直到超时清理仍未完成。
根因／修复筛查
本地修改：single-buffer 和 buffer-sequence 两条路径判定 done_and_exhausted 前均要求 !o->ec_。修复后的各错误路径三次均完成十次尝试；正常连接在有／无补丁时均通过。尚未取得上游接受或发布集成结果。
需要采集的证据
已采集：二进制生命周期、按代次保存的创建边、operation／frame 关联、reactor 状态及未改源程序的修复对照。
如何验证原始失败
使用 11 月 26 日上游附件中未改动的 standalone 协程版和回调版；Boost1.88.0 官方源码、Linux/GCC11.4。记录原 O2 构建与独立 O0 调试构建。正常连接和 buffer sequence 对照是明确标记的适配；未复现原 GoogleTest fixture 及 Ubuntu24.04/GCC13.3 环境。
环境与覆盖缺口
结论覆盖本地 Boost1.88.0 loopback 复现及所列对照。调试观测使用明确的 O0 重构建、匹配 ELF、激活区间及额外资源观察点；没有证明通用 stripped binary recall、生产开销、多线程泛化或定位耗时优势。
