最后一次 socket write 为什么不再完成？

CoroPerf 已补充的定位证据
CoroPerf 的二进制探针和既有实例图区分同一 frame 地址的多次寿命，并接回 writer。可选激活区间补足仅指令展开缺失的创建者证据；新增 Asio do_init 的 frame／handle 观察，把每次 write 接到正确的存活代次，再用 reactor 事件区分“操作仍排队”和“已完成却未恢复”。

展开证据与验证计划
已有证据

根因／修复筛查

需要采集的证据
已采集：二进制生命周期、按代次保存的创建边、operation／frame 关联、reactor 状态及未改源程序的修复对照。
如何验证原始失败

环境与覆盖缺口

怎样证明能更快定位

验证 coroperf 提供的执行与资源历史，能否缩短找到已验证根因的时间。列表中的案例用于检验这一主张，目前没有定位提速实测。

  1. 准入：保留 GitHub 原 revision、输入与失败特征，检查讨论及修复链接并记录审阅日期；已有根因或修复的条目退出首次根因定位队列。
  2. 原例：先用运行时常规诊断复现同一种失败；原环境不可用或配置冲突时标记 skipped 并注明原因，候选仍展示该障碍。
  3. 证据：以原生诊断为基线，在同一固定负载上补充 coroperf 身份、代次及所需资源事件；解释缺失事件前检查丢事件、观察点覆盖及采集开销。
  4. 定位比较：让独立分析者在相同故障与信息预算下，分别使用常规证据、常规证据加 coroperf；隐藏已知答案，跨案例平衡分析者与顺序以减少学习影响，保存时间戳及假设历程。
