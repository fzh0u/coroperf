Asio #1720：定位丢失的 write 完成事件

已建立调查案例；复现、诊断和修复结果待完成。

已重查主 issue 与可见活动；未取得仓库级补丁搜索和完整 API 历史。现有轨迹属于上游报告，不是本轮本地运行。

上游 issue · 案例记录

问题与已有证据

对端关闭后，写协程停住。上游评论报告回调版本也失败、禁用 epoll 后恢复，并已有 handler 与 frame 生命周期轨迹；这些是阶段性证据，尚未确证根因。

待区分的解释

假设区分证据
H1 · 前一次错误后，尚未结束的 write 丢失 reactor 进展。找到仍排队的操作代次，核对注册／就绪与缺少完成派发的证据，再定位队列／错误状态转换。
H2 · 操作已完成，但 continuation 没有被激活。必须先看到同一操作的完成事件，随后缺少匹配恢复；没有完成事件不能支持这一解释。
H3 · frame 存储复用混淆了寿命，或清理被误认为完成。对 frame 和操作分代，区分超时析构与 I/O 成功完成。

待采集的函数栈对比

本调查尚无采集栈或火焰图，以下是待验证的采集目标。

普通诊断增加 CoroPerf
handler tracking 已缩小到未结束的 write；worker 栈或函数符号不能区分同一 frame 地址的多次使用。目标是接回正确 writer 代次的逐操作事件链；必须对照 handler tracking 核实新增诊断价值，不能预设。

身份与事件链

  • writer 实例／代次 → 子 frame／代次
  • 子 frame → 显式 write 操作与 handler tag
  • 操作 → socket 代次、reactor 队列、就绪与派发
  • 完成 → 匹配恢复、最终挂起与析构

把 writer、复用的子 frame 代次与具体 write 操作关联，定位注册、就绪、完成、恢复链中第一个缺失的事件。

复现与对照

  1. 先在固定 Boost 1.88.0 上复现原测试，再启用 CoroPerf；须取得 TCPTest fixture 与 testTimeout，不把后续评论或新超时静默替代原例。
  2. 同一负载比较普通函数栈＋Asio handler tracking，与 CoroPerf frame 代次归属及明确增加的操作／reactor 观察。
  3. 回调版和禁用 epoll 版单列对照；回调也失败说明问题不局限于协程，后端变化本身不能确定错误转换。
  4. 隔离转换后，用未改动的回归测试与正常／错误路径对照验证针对原因的修复。本记录尚无修复或结果。
